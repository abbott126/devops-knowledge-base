Pod的生命周期

Pod 生命期

在 Pod 运行期间，kubelet 能够重启容器以处理一些失效场景。 在 Pod 内部，Kubernetes 跟踪不同容器的状态并确定使 Pod 重新变得健康所需要采取的动作。

Pod 在其生命周期中只会被调度一次。 将 Pod 分配到特定节点的过程称为绑定，而选择使用哪个节点的过程称为调度。 一旦 Pod 被调度并绑定到某个节点，Kubernetes 会尝试在该节点上运行 Pod。 Pod 会在该节点上运行，直到 Pod 停止或者被终止； 如果 Kubernetes 无法在选定的节点上启动 Pod（例如，如果节点在 Pod 启动前崩溃）， 那么特定的 Pod 将永远不会启动。

关联的生命周期

如果某物声称其生命期与某 Pod 相同，例如存储卷， 这就意味着该对象在此 Pod （UID 亦相同）存在期间也一直存在。 如果 Pod 因为任何原因被删除，甚至某完全相同的替代 Pod 被创建时， 这个相关的对象（例如这里的卷）也会被删除并重建。

Pod 阶段

Pod 的 status 字段是一个 PodStatus 对象，其中包含一个 phase 字段。

Pod 的阶段（Phase）是 Pod 在其生命周期中所处位置的简单宏观概述。 该阶段并不是对容器或 Pod 状态的综合汇总，也不是为了成为完整的状态机。

Pod 阶段的数量和含义是严格定义的。 除了本文档中列举的内容外，不应该再假定 Pod 有其他的 phase 值。

容器运行状态

Kubernetes 会跟踪 Pod 中每个容器的状态，就像它跟踪 Pod 总体上的阶段一样。 你可以使用容器生命周期回调 来在容器生命周期中的特定时间点触发事件。

一旦调度器将 Pod 分派给某个节点，kubelet 就通过容器运行时开始为 Pod 创建容器。容器的状态有三种：Waiting（等待）、Running（运行中）和 Terminated（已终止）。

要检查 Pod 中容器的状态，你可以使用 kubectl describe pod <pod 名称>。 其输出中包含 Pod 中每个容器的状态。

每种状态都有特定的含义：

Waiting（等待）

如果容器并不处在 Running 或 Terminated 状态之一，它就处在 Waiting 状态。 处于 Waiting 状态的容器仍在运行它完成启动所需要的操作：例如， 从某个容器镜像仓库拉取容器镜像，或者向容器应用 Secret 数据等等。 当你使用 kubectl 来查询包含 Waiting 状态的容器的 Pod 时，你也会看到一个 Reason 字段，其中给出了容器处于等待状态的原因。

!image-20251023153525241](/images/image-20251023153525241.png)

Running（运行中）

Running 状态表明容器正在执行状态并且没有问题发生。 如果配置了 postStart 回调，那么该回调已经执行且已完成。 如果你使用 kubectl 来查询包含 Running 状态的容器的 Pod 时， 你也会看到关于容器进入 Running 状态的信息。

Terminated（已终止）

处于 Terminated 状态的容器开始执行后，或者运行至正常结束或者因为某些原因失败。 如果你使用 kubectl 来查询包含 Terminated 状态的容器的 Pod 时， 你会看到容器进入此状态的原因、退出代码以及容器执行期间的起止时间。

  • Terminated（已终止）：表示资源已完全销毁，是最终状态；
  • Terminating（终止中）：是过渡状态，介于 “运行中” 和 “已终止” 之间。

如果容器配置了 preStop 回调，则该回调会在容器进入 Terminated 状态之前执行。

容器的重启策略

Pod 的 spec 中包含一个 restartPolicy 字段，其可能取值包括 Always、OnFailure 和 Never。默认值是 Always。

restartPolicy 应用于 Pod 中的应用容器和常规的 Init 容器。 Sidecar 容器忽略 Pod 级别的 restartPolicy 字段：在 Kubernetes 中，Sidecar 被定义为 initContainers 内的一个条目，其容器级别的 restartPolicy 被设置为 Always。 对于因错误而退出的 Init 容器，如果 Pod 级别 restartPolicy 为 OnFailure 或 Always， 则 kubelet 会重新启动 Init 容器。

  • Always：只要容器终止就自动重启容器。
  • OnFailure：只有在容器错误退出（退出状态非零）时才重新启动容器。
  • Never：不会自动重启已终止的容器

容器探针Container probes

在 Kubernetes 中，容器探针（Container Probes） 是用于监控容器健康状态的机制，Kubernetes 通过探针定期检查容器的运行状态，根据检查结果决定是否重启容器或调整流量路由，以保证应用的可用性。

探针的类型

Kubernetes 提供三种类型的探针，分别用于不同场景：

1. 存活探针（Liveness Probe）

  • 作用：判断容器是否 “存活”（运行正常）。如果探测失败，kubelet 会杀死该容器，并根据容器的 restartPolicy（重启策略）决定是否决定是否重启。
  • 典型用场景：检测应用死锁（如进程进程存在但无法响应请求），通过重启容器恢复服务。

2. 就绪探针（Readiness Probe）

  • 作用：判断容器是否 “就绪”（可以接收请求）。如果探测失败，Pod 会被从 Service 的 endpoints 中移除，不再接收流量。
  • 典型场景：应用启动时需要加载配置或数据（启动慢），就绪探针确保仅当应用完全准备好后才接收请求。

3. 启动探针（Startup Probe，K8s 1.16+ 新增）

  • 作用：判断容器内的应用是否 “启动完成”。仅在启动探针成功后，存活探针和就绪探针才会开始工作。
  • 典型场景：针对启动缓慢的应用（如大型 JVM 服务），避免存活探针在启动过程中误判为故障而重启容器。

探针的检测方式

每种探针都支持三种检测方法，可根据应用特性选择：

1. HTTP 检测（HTTP GET）

  • 向容器的指定端口和路径发送 HTTP GET 请求，返回状态码 200-399 视为成功。
  • 示例：检查 Web 服务的 /health 接口是否可用。
    livenessProbe:
      httpGet:
        path: /var/www/html/index.html
        port: 80
      initialDelaySeconds: 5  ## 启动后5秒开始首次探测
      periodSeconds: 5  # 每5秒探测一次

2. 命令检测（Exec）

  • 在容器内执行指定命令，若命令退出码为 0 视为成功。
  • 示例：执行 cat /tmp/healthy 检查文件是否存在，存在则认为健康。
apiVersion: v1
kind: Pod
metadata:
  name: web-server
spec:
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80
    args:
    - /bin/sh
    - -c
    - |
      mkdir -p  /var/www/html/;
      echo  "hello world" >  /var/www/html/index.html;
      sleep  60;
      rm -rf  /var/www/html/index.html;
      nginx -g 'daemon off;'
     livenessProbe:
       exec:
         command:
         - ls
         - /var/www/html/index.html
       initialDelaySeconds: 5  ## 启动后5秒开始首次探测
       periodSeconds: 5  # 每5秒探测一次
  • args 作用：Nginx 镜像默认启动命令是 nginx -g 'daemon off;'，这里通过 args 覆盖为自定义脚本，目的是在启动时创建 /var/www/html/index.html 文件（内容为 hello world），后续 Nginx 会默认加载该目录下的页面。

3. TCP 检测（TCP Socket）

  • 尝试与容器的指定端口建立 TCP 连接，连接成功视为成功。
  • 示例：检查数据库服务的 8080 端口是否可连接。
    livenessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 5  ## 启动后5秒开始首次探测
      periodSeconds: 5  # 每5秒探测一次

探针的配置参数

探针的行为可通过以下参数精细化控制：

  • initialDelaySeconds：容器启动后，首次探测的延迟时间（秒，默认 0）。
  • periodSeconds：探测的间隔时间（秒，默认 10）。
  • timeoutSeconds：单次探测的超时时间（秒，默认 1）。
  • successThreshold：探测失败后，连续多少次成功才算 “成功”（默认 1）。
  • failureThreshold：探测成功后，连续多少次失败才算 “失败”（默认 3）。

名称空间 namespaces

在 Kubernetes（K8s）中，Namespace（命名空间） 是用于对集群内资源进行逻辑隔离和分组管理的核心概念。它本质上是一个 “资源隔离容器”，可以将集群中的 Pod、Service、Deployment 等资源划分到不同的命名空间中，实现多团队、多环境的资源隔离与权限控制。

一、Namespace 的核心作用

  1. 资源隔离：不同命名空间中的资源名称可以重复（如两个命名空间都可创建名为 nginx 的 Pod），避免全局资源命名冲突。
  2. 环境隔离：可按环境划分命名空间（如 dev 开发环境、test 测试环境、prod 生产环境），确保不同环境的资源独立，避免测试操作影响生产。
  3. 权限与配额控制：结合 RBAC（基于角色的访问控制）可限制用户仅能操作特定命名空间的资源；同时可通过 ResourceQuota 为每个命名空间设置资源上限（如最大 CPU / 内存使用量），防止单个团队过度占用集群资源。
  4. 简化资源管理：通过命名空间过滤资源，避免集群资源过多时的管理混乱（如仅查看生产环境资源，无需关注开发环境）。

二、Kubernetes 内置的默认命名空间

K8s 集群初始化时会自动创建 4 个核心命名空间，用于承载不同类型的资源：

  1. default：默认命名空间，未指定命名空间的资源会自动归属此处（适合临时测试或简单场景）。
  2. kube-system：用于存放 Kubernetes 核心组件（如 kube-apiserver、kube-scheduler、kube-proxy 等）和系统级插件（如网络插件、监控插件）的资源，禁止用户随意修改。
  3. kube-public：公共命名空间，所有用户（包括未授权用户）均可访问，通常用于存放集群级的公共配置（如集群信息 ConfigMap）。
  4. kube-node-lease：用于存放节点的租约信息，K8s 通过此处的资源判断节点是否存活（1.13+ 版本引入，优化节点心跳机制）。

三、Namespace 的关键特性

  1. 命名空间的边界
  2. 隔离的资源：Pod、Service、Deployment、ConfigMap、Secret 等大部分核心资源。
  3. 不隔离的资源：Node（节点）、PersistentVolume（持久卷）等集群级资源（因为节点是物理 / 虚拟资源，PV 是全局共享的存储资源）。
  4. 跨命名空间访问：不同命名空间的资源可通过 “命名空间 + 资源名称” 的方式访问。例如，dev 命名空间的 Pod 要访问 prod 命名空间的 mysql Service，可通过 mysql.prod.svc.cluster.local（Service 的 DNS 格式：<service-name>.<namespace>.svc.<cluster-domain>）。
  5. 生命周期独立：删除命名空间时，会自动删除该命名空间下的所有资源（Pod、Service 等），但不会影响其他命名空间。

总结

Kubernetes 网络

kubernetes Network

集群的网络

网络是Kubernetes的核心部分，但要准确理解它是如何工作的可能具有挑战性。有4个不同的网络问题需要解决：

  1. 高度耦合的容器到容器通信：这可以通过以下方式解决豆荚和localhost通信。
  2. Pod-to-Pod沟通：这是本文档的主要重点。
  3. Pod-to-Service通信：服务涵盖此项。
  4. 外部与服务之间的通信：服务部门也涵盖此信息。

Kubernetes就是关于在应用程序之间共享机器。通常，共享机器需要确保两个应用程序不会尝试使用相同的端口。跨多个开发人员的端口协调规模非常困难，并且会暴露用户无法控制的集群级问题。

动态端口分配给系统带来了很多复杂功能——每个应用程序都必须将端口作为标志，API服务器必须知道如何将动态端口号插入到配置块中，服务必须知道如何找到彼此，等等。Kubernetes没有处理这个问题，而是采取了不同的方法。

Kubernetes IP地址范围

Kubernetes集群需要从以下组件中配置的一系列可用地址中为Pod、服务和节点分配非重叠的IP地址：

  • 网络插件被配置为为Pods分配IP地址。
  • kube-apiserver被配置为为服务分配IP地址。
  • kubelet或云控制器管理器被配置为为为节点分配IP地址。

Cluster networking types

负责配置的 IP 系列的 Kubernetes 集群可分为：

  • 仅 IPv4：网络插件 kube-apiserver 和 kubelet/cloud-controller-manager 配置为仅分配 IPv4 地址。
  • 仅 IPv6：网络插件 kube-apiserver 和 kubelet/cloud-controller-manager 配置为仅分配 IPv6 地址。
  • IPv4/IPv6 或 IPv6/IPv4 双栈 ：
  • 网络插件配置为分配 IPv4 和 IPv6 地址。
  • kube-apiserver 配置为分配 IPv4 和 IPv6 地址。
  • kubelet 或 cloud-controller-manager 配置为分配 IPv4 和 IPv6 地址。
  • 所有组件都必须就配置的主 IP 系列达成一致。

Kubernetes 集群仅考虑 Pod、Services 和 Nodes 对象上存在的 IP 系列，独立于所表示对象的现有 IP。例如，服务器或 Pod 的接口上可以有多个 IP 地址，但只有 node.status.addresses或 pod.status.ips 中的 IP 地址才能考虑实现 Kubernetes 网络模型和定义集群类型。

Pod 网络

是 Kubernetes 集群中实现 Pod 间通信、以及 Pod 与集群内外资源通信的关键机制。每个 Pod 都会被分配一个独立的 IP 地址，使其能够像虚拟机一样，通过 IP 地址进行寻址和通信。

Pod 网络的核心原则

Kubernetes 的网络模型设计遵循以下基本原则：

  • IP-Per-Pod：集群中的每个 Pod 都有一个唯一的 IP 地址。
  • 无需 NAT：所有 Pod 之间都可以直接使用各自的 Pod IP 地址进行通信，无需进行网络地址转换（NAT），无论这些 Pod 是否位于同一节点上。
  • 节点通信：节点上的代理（如 Kubelet）可以与该节点上的所有 Pod 进行通信。

Pod 内部通信

在单个 Pod 内，所有容器共享同一个网络命名空间、IP 地址和端口空间。这意味着 Pod 中的不同容器可以直接通过 localhost 或 127.0.0.1 相互通信。

Pod 间通信

Pod 间的通信模式根据 Pod 是否在同一节点上而有所不同，但对 Pod 本身是透明的。

  • 同一节点内：位于同一节点上的 Pods 可以通过该节点上的虚拟网络桥接进行通信，延迟较低。
  • 不同节点间：位于不同节点上的 Pods 之间的通信，则由底层的网络解决方案（CNI 插件）创建的覆盖网络（overlay network）或路由机制来处理。CNI 插件负责确保即使 Pod 位于不同物理节点上，Pod IP 也能正常路由。

实现 Pod 网络模型

Kubernetes 本身不提供 Pod 网络功能，而是通过以下组件和机制来定义和实现网络要求：

  • CNI（容器网络接口）：CNI 是一种标准接口，定义了网络插件如何为 Pod 分配 IP 地址和配置网络。当创建 Pod 时，kubelet 会调用配置好的 CNI 插件来完成网络设置。
  • CNI 插件：实现了 CNI 标准的插件，负责具体的网络配置工作。常见的 CNI 插件包括：
  • Calico：提供强大的网络策略和网络安全功能。
  • Flannel：轻量级、易于部署的覆盖网络解决方案。
  • Weave Net：提供简便的跨主机容器网络。
  • Cilium：基于 eBPF 技术，提供高性能网络和安全策略。
  • IP 地址管理（IPAM）：作为 CNI 的一部分，IPAM 负责为 Pod 分配唯一的 IP 地址。通常，每个节点会被分配一个不重叠的 Pod IP 地址段，然后该节点上的 Pods 将从这个地址段中获取 IP 地址。

Pod 网络的局限性和服务

由于 Pod 是短暂的（当 Pod 被重新创建时，其 IP 地址会改变），直接依赖 Pod IP 进行通信是不稳定的。为了解决这个问题，Kubernetes 引入了 Service 抽象：

  • Service：为一组 Pod 提供一个稳定的 IP 地址和 DNS 名称。客户端只需通过 Service 的 IP 地址或 DNS 名称访问，Service 会负责将请求负载均衡到后端健康的 Pod 上，从而隐藏了 Pod IP 地址动态变化的细节。

总而言之，Pod 网络是 Kubernetes 平台实现容器互联互通的基础，它通过 CNI 插件为每个 Pod 提供唯一的 IP 地址，并通过 Service 机制提供稳定的访问入口，确保了分布式应用的高效通信。

ingress

帮助k8s实现暴露到外部的一个控制器；

在 Kubernetes 中，Ingress 是管理集群外部访问集群内服务（通常是 HTTP/HTTPS 流量）的 API 资源，它提供了路由规则、域名绑定、SSL 终止、负载均衡等功能，是集群外部流量进入内部服务的 “入口网关”。

为什么需要 Ingress？

Kubernetes 中的 Service 虽然能暴露服务，但存在局限：

  • NodePort 会占用节点端口，且暴露方式不友好（需用 节点IP:端口 访问）。
  • LoadBalancer 依赖云厂商，成本较高，且每个服务都需要独立的负载均衡器。

Ingress 解决了这些问题：

  • 统一管理所有 HTTP/HTTPS 流量的路由规则。
  • 支持基于域名、路径的精细化路由（例如将 api.example.com 路由到 API 服务，web.example.com 路由到 Web 服务）。
  • 集中配置 SSL 证书，实现 HTTPS 加密。
  • 无需为每个服务单独暴露端口，通过一个入口点管理所有服务。

Ingress 的核心组成

  1. Ingress 资源：通过 YAML 定义的路由规则（如域名、路径、后端服务等）。

  2. Ingress 控制器（Ingress Controller）

：实际执行路由规则的组件（如 Nginx、Traefik 等），是 Ingress 功能的 “执行者”。

注意：仅创建 Ingress 资源无效，必须先部署 Ingress 控制器，否则规则不会生效。

常见 Ingress 控制器

  • Nginx Ingress Controller：最常用，基于 Nginx 反向代理实现，支持丰富的配置。
  • Traefik：云原生网关，自动发现服务，配置简单，适合动态环境。
  • Cilium Ingress Controller 是由 Cilium 提供的 ingress controller。
  • HAProxy Ingress：基于 HAProxy，性能优秀，适合高并发场景。
  • Istio Ingress Gateway：服务网格 Istio 的入口组件，支持更复杂的流量治理（如熔断、限流）。

实现LB

基于云厂商

纯软件解决方案：MetalLB

MetalLB 为不运行在受支持云提供商上的 Kubernetes 集群提供了网络负载均衡器实现，有效地允许在任何集群中使用 LoadBalancer 服务。

MetalLB 是专门为裸金属（Bare-metal）Kubernetes 集群设计的 LoadBalacer 实现，可解决本地集群（非云环境）中 Service 类型为 LoadBalancer 时无法分配外部 IP 的问题（云厂商通常通过自家 LB 服务自动分配 IP，本地集群无此能力）。

一、MetalLB 工作原理

MetalLB 会为集群中的 LoadBalancer 类型 Service 分配一个预配置的静态 IP 池中的 IP，并通过以下两种模式将 IP 暴露到集群外部：

  1. Layer 2 模式（二层模式）：通过 ARP/NDP 协议在本地局域网广播 IP 映射，使该 IP 与集群中某节点绑定（类似 “浮动 IP”），适合小型网络。
  2. BGP 模式（三层模式）：通过 BGP 协议与外部路由器通信，动态宣告 IP 路由，适合大规模网络或需要更高可用性的场景。

最常用的是 Layer 2 模式（配置简单，无需路由器支持）。

二、部署 MetalLB 步骤（以 Layer 2 模式为例）

  1. 前提条件

  2. Kubernetes 集群版本 ≥ v1.19（推荐 v1.24+）。

  3. 集群未启用云厂商的 LoadBalancer 控制器（如 GKE、EKS 自带的 LB，本地集群默认满足）。

  4. 准备一个未被局域网中其他设备占用的 IP 段（作为 MetalLB 的 IP 池，例如 192.168.1.200-192.168.1.210）。

  5. 安装 MetalLB

推荐用官方 Manifest 部署（适用于大多数集群）：

四、关键配置说明

  1. IP 池规划

  2. IP 段必须在局域网网段内（如 192.168.1.0/24），且未被其他设备使用（避免 IP 冲突）。

  3. 可配置多个 IP 池（多个 IPAddressPool），并通过 L2Advertisement 关联不同池。

  4. 高可用（Layer 2 模式）

  5. Layer 2 模式下，MetalLB 会将 IP 绑定到集群中的一个节点（“领导者” 节点），若该节点故障，会自动漂移到其他节点（约 10-30 秒切换）。

  6. 需确保节点间网络互通，且防火墙允许 ARP 广播（否则 IP 漂移可能失败）。

  7. BGP 模式（可选）

若局域网有支持 BGP 的路由器（如 Cisco、Juniper），可配置 BGP 模式实现更灵活的路由控制（如跨子网访问），需额外定义 BGPPeer 资源关联路由器。

五、常见问题解决
  1. Service 一直处于 <pending> 状态
  2. 检查 MetalLB 组件是否正常运行：kubectl logs -n metallb-system <controller-pod>。
  3. 确认 IP 池配置正确（IP 段未被占用，且在局域网内）。
  4. 外部无法访问分配的 EXTERNAL-IP
  5. 检查节点防火墙是否开放 Service 对应的端口（Layer 2 模式下，流量会先到绑定 IP 的节点，再转发到 Pod）。
  6. 确认本地电脑与 EXTERNAL-IP 网段互通（如 ping 192.168.1.200 测试）。
  7. IP 冲突
  8. 确保 IP 池中的 IP 未被其他设备使用（可通过 arp-scan 工具扫描局域网 IP 占用情况）。
六、总结

MetalLB 是本地 Kubernetes 集群实现 LoadBalancer 类型 Service 的最佳方案，通过 Layer 2 模式可快速部署，解决外部 IP 分配问题。只需规划好 IP 池，即可让集群中的服务像云环境一样通过固定 IP 暴露，无需手动配置 NodePort 或第三方 LB。

工作负载管理

工作负载管理 workload manager

在 Kubernetes（K8s）中，控制器（Controller） 是实现集群状态自动化管理的核心组件，它遵循 “声明式 API” 理念：用户通过 YAML 定义资源的 “期望状态”，控制器持续监控集群的 “实际状态”，并通过一系列操作将实际状态向期望状态推进。

简单来说，控制器就是 K8s 中的 “自动化运维工具”，负责 Pod 的创建、扩缩容、自愈、更新等核心操作，避免人工干预。

控制器的核心工作原理

  1. 监听状态：通过 API Server 实时监听目标资源（如 Pod、Deployment）的状态变化。
  2. 对比状态：将 “实际状态” 与用户定义的 “期望状态” 进行对比。
  3. 执行调和（Reconciliation）：若实际状态与期望状态不一致，控制器会触发一系列操作（如创建 Pod、删除异常实例、调整副本数），直到两者一致。

这个 “监听 - 对比 - 调和” 的循环，是所有 K8s 控制器的核心逻辑。

K8s 中常用的核心控制器

1. Deployment（部署控制器）

  • 核心作用：管理无状态应用，提供 Pod 的创建、扩缩容、滚动更新、回滚等功能，是最常用的控制器。
  • 关键特性
  • 支持设n，自动维持 Pod 数量（如 Pod 异常退出时自动重启）。
  • 滚动更新（Rolling Update）：逐步替换旧版本 Pod，确保服务不中断。
  • 回滚（Rollback）：若更新失败，可快速回滚到之前的稳定版本。
  • 适用场景：Web 服务、API 接口等无状态应用（无需持久化存储，实例可随意替换）。

2. StatefulSet（有状态集控制器）

  • 核心作用：管理有状态应用，解决 Deployment 无法满足的有状态场景需求。
  • 关键特性
  • 为每个 Pod 分配固定的名称（格式：<statefulset-name>-<ordinal-index>，如 mysql-0、mysql-1）和网络标识（通过 Headless Service 实现固定 DNS）。
  • 支持有序部署 / 删除（按序号从 0 到 N-1 启动，反向停止）。
  • 与 PersistentVolumeClaim（PVC）模板结合，为每个 Pod 分配独立的持久化存储（避免数据共享冲突）。
  • 适用场景：数据库（MySQL、PostgreSQL）、分布式存储（Elasticsearch、ZooKeeper）等需要固定标识和独立存储的应用。

3. DaemonSet（守护进程集控制器）

  • 核心作用：确保集群中所有（或指定）节点上都运行一个相同的 Pod 副本，类似传统的 “守护进程”。
  • 关键特性
  • 新节点加入集群时，自动在该节点上创建对应的 Pod；节点移除时，自动删除 Pod。
  • 支持通过节点选择器（nodeSelector）或亲和性规则，仅在特定节点上部署 Pod。
  • 适用场景：日志收集（Fluentd、Logstash）、监控代理（Prometheus Node Exporter）、网络插件（Calico、Flannel）等需要在每个节点上运行的服务。

4. ReplicaSet（副本集控制器）

  • 核心作用：确保集群中始终运行指定数量的 Pod 副本，是 Deployment 的底层依赖（Deployment 通过控制 ReplicaSet 实现副本管理）。
  • 关键特性：仅负责维持副本数，不支持滚动更新、回滚等高级功能。
  • 注意：实际使用中，优先选择 Deployment 而非直接使用 ReplicaSet，因为 Deployment 提供了更完整的生命周期管理能力。

5. Job（任务控制器）

  • 核心作用：管理一次性任务（批处理任务），确保任务执行完成后终止 Pod。
  • 关键特性
  • 任务成功完成后，Pod 状态变为 Succeeded，不再重启。
  • 支持并行执行多个任务（通过 parallelism 配置并行数）。
  • 适用场景：数据备份、批量计算、一次性脚本执行等短期任务。

6. CronJob（定时任务控制器）

  • 核心作用：管理周期性执行的任务，类似 Linux 中的 crontab。
  • 关键特性
  • 通过 schedule 字段定义执行周期（如 0 3 * * * 表示每天凌晨 3 点执行）。
  • 支持配置任务超时时间、失败重试策略等。
  • 适用场景：定时数据清理、定时报表生成、定时备份等周期性任务。

7. HorizontalPodAutoscaler（HPA，水平 Pod 自动扩缩容控制器）

  • 核心作用：根据 Pod 的 CPU / 内存使用率或自定义指标（如请求量），自动调整控制器（Deployment、StatefulSet 等）的副本数，实现弹性伸缩。
  • 关键特性
  • 支持设置最小副本数和最大副本数，避免扩缩容过度。
  • 可结合监控系统（如 Prometheus）获取自定义指标。
  • 适用场景：流量波动较大的应用（如电商促销期间自动扩容，低峰期自动缩容，节省资源）。

控制器与 Pod 的关系

  • 控制器不直接管理 Pod，而是通过 “控制循环” 间接操作：用户定义控制器的期望状态（如 Deployment 的 replicas: 3），控制器根据该状态创建 / 删除 Pod，或调整 Pod 的数量。
  • Pod 是控制器的 “被管理对象”，控制器确保 Pod 的状态始终符合期望。例如，Deployment 管理的 Pod 若因节点故障被删除，Deployment 会立即在其他健康节点上创建新的 Pod 以维持副本数。

总结

K8s 控制器的核心价值是 “自动化运维”，通过不同类型的控制器，可满足无状态、有状态、守护进程、定时任务等多种业务场景的需求。实际使用中，需根据应用的特性选择合适的控制器：

  • 无状态应用 → Deployment
  • 有状态应用 → StatefulSet
  • 节点级服务 → DaemonSet
  • 一次性任务 → Job
  • 定时任务 → CronJob
  • 弹性伸缩 → HPA

rollout：管理资源的滚动更新（如 Deployment 的版本升级、回滚等操作）

scale：为 Deployment（部署控制器）、ReplicaSet（副本集）或 Replication Controller（复制控制器）设置新的副本数量（即调整资源的实例规模）

autoscale：为 Deployment、ReplicaSet、StatefulSet（有状态集）或 Replication Controller 配置自动扩缩容（根据 CPU 使用率、自定义指标等自动调整副本数）

示例：

# apiVersion：指定 Kubernetes API 版本，Deployment 属于 apps 组，版本为 v1
apiVersion: apps/v1
# kind：定义资源类型，这里是 Deployment（部署控制器）
kind: Deployment
# metadata：资源的元数据，用于标识和描述 Deployment
metadata:
  name: nginx-deployment  # Deployment 的名称（唯一标识）
  labels:  # 给 Deployment 自身打的标签（用于分类或关联其他资源）
    app: nginx  # 标签键值对，键为 app，值为 nginx
# spec：Deployment 的核心配置，定义期望状态
spec:
  # replicas：期望运行的 Pod 副本数（控制器会自动维持这个数量）
  replicas: 3
  # selector：选择器，用于关联被管理的 Pod（通过标签匹配）
  selector:
    matchLabels:  # 匹配标签：仅管理带有 app: nginx 标签的 Pod
      app: nginx
  # template：Pod 模板，定义要创建的 Pod 的规格（Deployment 根据此模板生成 Pod）
  template:
    # metadata：Pod 的元数据
    metadata:
      labels:  # 给 Pod 打的标签（必须与上面的 selector.matchLabels 匹配，否则无法被管理）
        app: nginx
    # spec：Pod 的具体配置（包含容器信息）
    spec:
      # containers：Pod 中运行的容器列表（这里只有一个 Nginx 容器）
      containers:
      - name: nginx  # 容器名称（在 Pod 内唯一）
        image: nginx:1.14.2  # 容器使用的镜像（Nginx 1.14.2 版本）
        ports:  # 容器暴露的端口（仅用于标识，不自动映射到宿主机）
        - containerPort: 80  # 容器内 Nginx 实际监听的端口（默认 80）

更新策略

strategy:  # 定义 Deployment 的更新策略（控制如何替换旧版本 Pod）
  rollingUpdate:  # 滚动更新的具体参数配置
    maxSurge: 25%  # 允许超出期望副本数的最大比例（或绝对值）
                   # 含义：更新过程中，集群中同时运行的 Pod 总数最多比期望副本数（replicas）多 25%
                   # 示例：若 replicas=4，最多可同时运行 4 + 4×25% = 5 个 Pod（先创建 1 个新 Pod 再删除旧 Pod）
    maxUnavailable: 25%  # 允许不可用的 Pod 最大比例（或绝对值）
                         # 含义：更新过程中，不可用的 Pod 数量最多不超过期望副本数的 25%
                         # 示例：若 replicas=4，最多允许 4×25% = 1 个 Pod 不可用（每次删除旧 Pod 不超过 1 个）
  type: RollingUpdate  # 指定更新策略类型为滚动更新（Kubernetes 的默认策略）

Clean up Policy 清理策略

spec:
  # 1. 进度超时时间：控制 Deployment 更新的最大容忍时间
  progressDeadlineSeconds: 600  # 单位：秒（600秒 = 10分钟）
                                # 含义：若 Deployment 更新（如滚动更新）超过 10 分钟仍未完成（未达到可用状态），
                                # Kubernetes 会将其标记为“更新失败”（Progressing 状态变为 False，Reason 为 ProgressDeadlineExceeded），
                                # 但不会自动终止更新，需手动处理（如回滚、调整参数后重试）。

  # 2. 副本数：定义期望运行的 Pod 数量
  replicas: 1  # 期望保持 1 个 Pod 副本运行
               # Deployment 会通过控制器逻辑自动维持这个数量（如 Pod 故障时重建）。

  # 3. 历史版本保留限制：控制旧 ReplicaSet 的保留数量
  revisionHistoryLimit: 10  # 默认为 10，表示最多保留 10 个旧版本的 ReplicaSet（每个 ReplicaSet 对应一次 Deployment 更新）
                            # 超过此数量后，最旧的 ReplicaSet 会被自动删除，释放资源。
                            # 作用：旧 ReplicaSet 用于回滚操作（`kubectl rollout undo`），保留适量历史版本可兼顾回滚需求和资源消耗。

核心作用总结

  • progressDeadlineSeconds：防止更新过程无限期阻塞，为更新设置 “超时门槛”，便于及时发现更新异常（如镜像拉取失败、探针检测不通过导致的更新卡壳）。
  • replicas：定义应用的实例数量，是 Deployment 实现 “自愈” 和 “扩缩容” 的基础（结合 kubectl scale 可手动调整，结合 HPA 可自动调整）。
  • revisionHistoryLimit：平衡历史版本管理和资源占用，避免旧 ReplicaSet 过多导致集群资源浪费（尤其频繁更新的 Deployment）。

StatefulSet

是用于管理有状态的应用工作负载 API 对象。

Example: 

# API 版本，StatefulSet 在 apps/v1 版本中定义
apiVersion: apps/v1
# 资源类型为 StatefulSet（有状态集合，用于管理有状态应用）
kind: StatefulSet
metadata:
  # StatefulSet 的名称，用于标识该资源
  name: web
spec:
  # 选择器：用于匹配要管理的 Pod 标签，必须与下面 template.metadata.labels 一致
  selector:
    matchLabels:
      app: nginx # 匹配标签为 app: nginx 的 Pod
  # 服务名称：为 StatefulSet 中的 Pod 提供稳定网络标识的 Headless Service 名称
  # 需提前创建名为 nginx 的 Headless Service（无 ClusterIP）
  serviceName: "nginx"
  # 副本数：指定要运行的 Pod 数量，这里为 3 个
  replicas: 3 # 默认值为 1
  # 最小就绪秒数：Pod 就绪后等待多久才视为可用，避免频繁切换状态
  minReadySeconds: 10 # 默认值为 0
  # Pod 模板：定义 StatefulSet 生成的 Pod 的规格
  template:
    metadata:
      # Pod 的标签，必须与 spec.selector.matchLabels 匹配
      labels:
        app: nginx
    spec:
      # 终止宽限期：删除 Pod 时等待的秒数，确保优雅关闭
      terminationGracePeriodSeconds: 10
      # 容器配置列表
      containers:
      - name: nginx # 容器名称
        image: nginx:latest # 使用的镜像（最新版 Nginx）
        # 容器暴露的端口配置
        ports:
        - containerPort: 80 # 容器内监听的端口
          name: web # 端口名称，用于标识
        # 卷挂载：将存储卷挂载到容器内的指定路径
        volumeMounts:
        - name: www # 要挂载的卷名称（需与下面 volumes.name 对应）
          mountPath: /usr/share/nginx/html/index.html # 容器内的挂载路径（Nginx 默认首页位置）
      # 存储卷定义：供容器挂载的卷
      volumes:
      - name: www # 卷名称，与 volumeMounts.name 对应
        # 使用 hostPath 卷：将节点（宿主机）的路径挂载到容器
        hostPath:
          # 宿主机上的路径（这里指向宿主机的 /opt/index.html 文件）
          path: /opt/index.html
          # 路径类型：如果宿主机上不存在该文件，则自动创建一个空文件
          type: FileOrCreate
          # 其他可选类型说明：
          # - DirectoryOrCreate：路径不存在则创建目录
          # - Directory：必须存在目录，否则挂载失败
          # - File：必须存在文件，否则挂载失败
          # - Socket：必须存在 socket 文件
          # - CharDevice：必须存在字符设备
          # - BlockDevice：必须存在块设备

存储管理

Storage 存储

Volumes 卷

1. 为什么需要卷

2. How volumes work 卷的工作原理

Kubernetes 支持多种类型的卷

  • 临时数据卷： K8s 会被清除

  • 永久数据卷： k8s 不会删除

核心来说，一个卷就是一个目录，可能包含一些数据，并且该目录可以被 pod 中的容器访问。该目录是如何形成的，其背后的存储介质以及其中的内容是由所使用的特定卷类型决定的。

要使用卷，请在 Pod 中指定要提供的卷 .spec.volumes ，并在容器中声明将这些卷挂载到何处 .spec.containers[*].volumeMounts 。

类似：container

1. 创建数据卷 docker volume  create 
2. 创建容器 docker run

3. Types of volumes 卷类型

configMap 配置映射

ConfigMap 提供了一种将配置数据注入到 Pod 中的方法。 存储在 ConfigMap 中的数据可以在类型为 的卷中引用。 configMap ，然后由在 pod 中运行的容器化应用程序使用。

emptyDir 空目录

对于定义了 emptyDir 卷的 Pod，该卷会在 Pod 被分配到节点时创建。顾名思义， emptyDir卷初始状态为空。Pod 中的所有容器都可以读写 emptyDir 卷中的相同文件，但每个容器中该卷的挂载路径可以相同也可以不同。当 Pod 由于任何原因从节点移除时， emptyDir 中的数据将被永久删除。

emptyDir 的核心特性
  1. 生命周期与 Pod 绑定：
  2. emptyDir 随着 Pod 的创建而创建，随着 Pod 的删除而删除（即使 Pod 内的容器重启，数据也会保留）。
  3. 当 Pod 被调度到新节点时，会在新节点上创建新的 emptyDir，原节点上的 emptyDir 会被删除。
  4. 存储位置：
  5. 默认存储在节点的本地磁盘（由节点的文件系统管理）。
  6. 若节点配置了 tmpfs（内存文件系统），可指定 emptyDir 存储在内存中（速度更快，但数据易失，且受节点内存限制）。
  7. 用途：
  8. 容器间共享临时数据（例如，前端容器生成的文件需要后端容器处理）。
  9. 存储应用运行时产生的临时缓存、日志（无需持久化的场景）。

Example: dome 示例

# 指定 Kubernetes API 版本，Pod 资源属于 v1 核心组
apiVersion: v1
# 定义资源类型为 Pod
kind: Pod

  # Pod 的名称，在命名空间内唯一
  name: test-pd
spec:
  # 定义 Pod 中的容器列表
  containers:
  - # 容器使用的镜像（这里是 Kubernetes 官方测试用的 Web 服务器镜像）
    image: registry.k8s.io/test-webserver
    # 容器的名称，在 Pod 内唯一
    name: test-container
    # 定义容器需要挂载的卷
    volumeMounts:
    - # 卷在容器内的挂载路径（容器内的 /cache 目录会关联到 emptyDir 卷）
      mountPath: /cache
      # 要挂载的卷名称（需与下面 volumes 中定义的卷名一致）
      name: cache-volume
  # 定义 Pod 可用的卷列表
  volumes:
  - # 卷的名称（供 volumeMounts 引用）
    name: cache-volume
    # 定义卷类型为 emptyDir（临时空目录卷）
    emptyDir:
      # 限制 emptyDir 的最大存储空间为 500MiB
      # 超出此限制时，Pod 可能会被 Kubernetes 标记为失败
      sizeLimit: 500Mi
  • emptyDir 卷是临时存储，生命周期与 Pod 一致，Pod 删除后数据会丢失
  • sizeLimit 是可选配置，用于限制卷的最大使用空间（防止容器过度占用节点存储）
  • volumeMounts 实现了将卷挂载到容器内的指定路径，使容器可以读写该卷中的数据

iscsi

ISCSI（Internet Small Computer System Interface，互联网小型计算机系统接口）是一种基于 TCP/IP 协议的存储网络技术，核心作用是将远程存储设备（如磁盘阵列）通过网络模拟为本地块设备，让客户端（服务器）像使用本地硬盘一样读写远程存储。

iscsi 卷允许将现有的 iSCSI（基于 IP 的 SCSI）卷挂载到 Pod 中。与 emptyDir 不同，emptyDir 会在 Pod 移除时被擦除，而 iscsi 卷的内容会被保留，卷本身只是被卸载。这意味着 iSCSI 卷可以预先填充数据，并且这些数据可以在 Pod 之间共享。

local 本地卷

local 卷是指已挂载的本地存储设备，例如磁盘、分区或目录。

本地卷只能用作静态创建的持久卷。不支持动态配置。

与 hostPath 卷相比， local 卷以持久且可移植的方式使用，无需手动将 Pod 调度到节点。系统通过查看 PersistentVolume 上的节点亲和性来了解卷的节点约束。

nfs

nfs 卷允许将现有的 NFS（网络文件系统）共享挂载到 Pod 中。与在 Pod 移除时会被擦除的 emptyDir 不同， nfs 卷的内容会被保留，卷本身只是被卸载。这意味着 NFS 卷可以预先填充数据，并且这些数据可以在 Pod 之间共享。NFS 卷可以同时被多个写入器挂载。

NFS协议分为以下几个层次：

应用层：提供文件系统操作接口，如 mount 、 nfsstat 等。

传输层：使用RPC（远程过程调用）进行通信，确保数据传输的可靠性和完整性。

网络层：使用TCP或UDP协议进行数据传输。

NFS的工作流程如下： 客户端向服务器发送请求，请求共享文件系统的访问权限。 服务器检查客户端的权限，并返回访问权限。 客户端使用挂载命令将文件系统挂载到本地目录。 客户端可以访问共享文件系统中的文件和目录。 编辑 /etc/exports 文件，添加共享目录和客户端访问权限。 使用 exportfs 命令刷新exports文件，使配置生效。

Persistent Volumes 持久卷 pv

存储管理与计算实例管理是截然不同的问题。PersistentVolume 子系统为用户和管理员提供了一个 API，它将存储的提供方式与使用方式隔离开来。为此，我们引入了两个新的 API 资源：PersistentVolume 和 PersistentVolumeClaim。

持久卷 (PV) 是集群中一块已部署的存储区域。 由管理员配置或使用动态方式配置 存储类 。它就像集群中的节点一样，是一种集群资源。PV 是卷插件，类似于卷，但其生命周期独立于使用该 PV 的任何单个 Pod。此 API 对象捕获存储实现的详细信息，无论是 NFS、iSCSI 还是云提供商特定的存储系统。

持久卷声明 (PVC) 是用户对存储的请求。它类似于 Pod。Pod 消耗节点资源，而 PVC 消耗持久卷资源。Pod 可以请求特定级别的资源（CPU 和内存）。声明可以请求特定大小和访问模式（例如，可以挂载为 ReadWriteOnce、ReadOnlyMany、ReadWriteMany 或 ReadWriteOncePod，请参阅 AccessModes ）。

虽然 PersistentVolumeClaims 允许用户使用抽象的存储资源，但用户通常需要具有不同属性（例如性能）的 PersistentVolume 来解决不同的问题。集群管理员需要能够提供各种 PersistentVolume，这些卷的差异不仅体现在大小和访问模式上，还体现在其他方面，同时还要避免让用户了解这些卷的具体实现细节。为了满足这些需求，可以使用 StorageClass 资源。

Lifecycle of a volume and claim

PV 是集群中的资源。PVC 是对这些资源的请求，同时也充当对资源的声明检查。PV 和 PVC 之间的交互遵循以下生命周期

Provisioning：

PV 的配置方式有两种：静态配置或动态配置

静态：

集群管理员创建多个 PV（持久存储）。这些 PV 承载着实际存储的详细信息，可供集群用户使用。它们存在于 Kubernetes API 中，可供调用。

动态：

当管理员创建的静态 PV 中没有一个与用户的 PersistentVolumeClaim 匹配时， 集群可能会尝试动态地专门为 PVC 配置一个卷。 此配置基于存储类：PVC 必须请求一个 要启用动态配置，必须指定存储类， 并且管理员必须创建并配置该类。请求该类的声明（例如 "" 实际上会禁用自身的动态配置。

# 访问模式Access Modes:

访问模式Access Modes:

在 Kubernetes 中，accessModes（访问模式）用于定义 PersistentVolume（PV） 或 PersistentVolumeClaim（PVC） 对存储资源的访问策略，决定了存储可以被多少节点或 Pod 以何种方式挂载

访问模式的值 含义
ReadWriteOnce（RWO） 仅允许 单个节点 以 读写（Read-Write） 方式挂载该存储。
ReadOnlyMany（ROX） 允许多个节点以 只读（Read-Only） 方式挂载该存储。
ReadWriteMany（RWX 允许多个节点以 读写（Read-Write） 方式挂载该存储。
ReadWriteOncePod（RWOP） 仅允许 单个 Pod 以读写方式挂载该存储（Kubernetes 1.27+ 版本新增）。

StorageClass（存储类)

在 Kubernetes 中，StorageClass（存储类） 是用于对集群存储资源进行分类和管理的 API 资源，核心作用是 “定义存储类型模板”，实现存储的动态供给（自动创建 PV）和按需匹配（让 PVC 快速找到符合需求的存储），解决了静态 PV 需手动创建的低效问题。

一、核心价值：为什么需要 StorageClass？

没有 StorageClass 时，使用存储需管理员手动创建 PV，存在两大痛点：

  1. 效率低：集群规模大时，手动创建大量 PV 运维成本高。
  2. 匹配难：用户需了解底层存储细节（如 NFS 路径、云盘类型）才能申请 PVC。

StorageClass 通过以下方式解决：

  • 动态供给：用户创建 PVC 时，K8s 会根据 StorageClass 配置，自动创建对应的 PV 和底层存储（如自动创建 AWS EBS 卷、NFS 目录）。
  • 抽象存储细节：用户只需指定 StorageClass 名称（如 fast-ssd、slow-hdd），无需关心底层是云盘还是本地存储。
  • 分类管理：按存储性能（SSD/HDD）、用途（数据库 / 日志）、厂商（AWS/Azure）分类，满足不同应用需求。

二、StorageClass 的核心配置

apiVersion: storage.k8s.io/v1  # 固定 API 版本
kind: StorageClass             # 资源类型
metadata:
  name: fast-ssd               # StorageClass 名称（用户申请时需指定）
provisioner: kubernetes.io/aws-ebs  # 存储供给器（核心！决定用哪种存储插件）
parameters:                    # 存储参数（随供给器变化，定义存储具体属性）
  type: gp3                    # AWS EBS 卷类型（通用型 SSD）
  fsType: xfs                  # 文件系统类型
reclaimPolicy: Delete          # 回收策略（PV 释放后自动删除，默认 Delete）
allowVolumeExpansion: true     # 是否允许 PVC 扩容（需底层存储支持）
volumeBindingMode: WaitForFirstConsumer  # 卷绑定时机（关键！控制 PV 何时创建）
字段 作用说明
provisioner 存储供给器：对接底层存储的插件（如 kubernetes.io/aws-ebs 对应 AWS 云盘，kubernetes.io/nfs 对应 NFS），决定能否动态创建 PV。👉 注意：若为 “手动管理的存储”（如本地卷），需设为 kubernetes.io/no-provisioner，表示不支持动态供给。
parameters 存储的具体属性（随供给器变化）：
- 云盘：卷类型（如 gp3）、加密配置等；
- NFS：服务器地址（server）、共享目录（path）等。
reclaimPolicy PV 回收策略，默认 Delete（动态创建的 PV 随 PVC 删除而删除），可选 Retain（保留 PV 和数据，需手动清理）。
allowVolumeExpansion 是否允许 PVC 扩容（如 PVC 申请 5Gi 后可扩容到 10Gi），需底层存储支持（如 AWS EBS、NFS 支持，本地卷部分支持）。
volumeBindingMode 卷绑定时机（控制 PV 何时与 PVC 绑定）：
- Immediate（默认）：PVC 创建后立即绑定 PV（适合无节点依赖的存储，如 NFS）；
- WaitForFirstConsumer（延迟绑定）：等待第一个使用该 PVC 的 Pod 调度后，再根据 Pod 节点亲和性创建 / 绑定 PV（适合本地卷、云盘等节点绑定的存储，避免 PV 与 Pod 不在同一节点）。

Secrets 密钥

A Secret is an object that contains a small amount of sensitive data such as a password, a token, or a key. Such information might otherwise be put in a Pod specification or in acontainer image. Using a Secret means that you don't need to include confidential data in your application code.
秘密对象是指包含少量敏感数据的对象，例如： 密码、令牌或密钥。此类信息也可能被放入……Pod 规格或在 容器镜像 。使用密钥意味着您无需在应用程序代码中包含机密数据。

由于 Secret 的创建可以独立于使用它们的 Pod，因此在创建、查看和编辑 Pod 的工作流程中，Secret（及其数据）泄露的风险更低。Kubernetes 以及在集群中运行的应用程序还可以对 Secret 采取额外的预防措施，例如避免将敏感数据写入非易失性存储。

警告：

默认情况下，Kubernetes Secret 以未加密的形式存储在 API 服务器的底层数据存储（etcd）中。任何拥有 API 访问权限的用户都可以检索或修改 Secret，任何拥有 etcd 访问权限的用户也可以这样做。此外，任何被授权在命名空间中创建 Pod 的用户都可以使用该权限读取该命名空间中的任何 Secret；这包括间接访问，例如创建 Deployment 的权限

调度

调度、抢占和驱逐

在 Kubernetes 中，调度（scheduling）指的是确保 Pod 匹配到合适的节点， 以便 kubelet 能够运行它们。 抢占（Preemption）指的是终止低优先级的 Pod 以便高优先级的 Pod 可以调度到 Node 上的过程。 驱逐（Eviction）是在资源匮乏的节点上，主动让一个或多个 Pod 失效的过程。

Kubernetes 调度器

在 Kubernetes 中，调度是指将 Pod 放置到合适的节点上，以便对应节点上的 Kubelet 能够运行这些 Pod。

调度概览

调度器通过 Kubernetes 的监测（Watch）机制来发现集群中新创建且尚未被调度到节点上的 Pod。 调度器会将所发现的每一个未调度的 Pod 调度到一个合适的节点上来运行。 调度器会依据下文的调度原则来做出调度选择。

如果你想要理解 Pod 为什么会被调度到特定的节点上， 或者你想要尝试实现一个自定义的调度器，这篇文章将帮助你了解调度。

kube-scheduler

kube-scheduler 是 Kubernetes 集群的默认调度器，并且是集群 控制面 的一部分。 如果你真的希望或者有这方面的需求，kube-scheduler 在设计上允许你自己编写一个调度组件并替换原有的 kube-scheduler。

Kube-scheduler 选择一个最佳节点来运行新创建的或尚未调度（unscheduled）的 Pod。 由于 Pod 中的容器和 Pod 本身可能有不同的要求，调度程序会过滤掉任何不满足 Pod 特定调度需求的节点。 或者，API 允许你在创建 Pod 时为它指定一个节点，但这并不常见，并且仅在特殊情况下才会这样做。

在一个集群中，满足一个 Pod 调度请求的所有节点称之为可调度节点。 如果没有任何一个节点能满足 Pod 的资源请求， 那么这个 Pod 将一直停留在未调度状态直到调度器能够找到合适的 Node。

调度器先在集群中找到一个 Pod 的所有可调度节点，然后根据一系列函数对这些可调度节点打分， 选出其中得分最高的节点来运行 Pod。之后，调度器将这个调度决定通知给 kube-apiserver，这个过程叫做绑定。

在做调度决定时需要考虑的因素包括：单独和整体的资源请求、硬件/软件/策略限制、 亲和以及反亲和要求、数据局部性、负载间的干扰等等。

kube-scheduler 中的节点选择

kube-scheduler 给一个 Pod 做调度选择时包含两个步骤：

  1. 过滤
  2. 打分

过滤阶段会将所有满足 Pod 调度需求的节点选出来：

例如: PodFitsResources过滤函数会检查候选节点的可用资源能否满足 Pod 的资源请求。 在过滤之后，得出一个节点列表，里面包含了所有可调度节点；通常情况下， 这个节点列表包含不止一个节点。如果这个列表是空的，代表这个 Pod 不可调度。

在打分阶段，调度器会为 Pod 从所有可调度节点中选取一个最合适的节点。 根据当前启用的打分规则，调度器会给每一个可调度节点进行打分。

最后，kube-scheduler 会将 Pod 调度到得分最高的节点上。 如果存在多个得分最高的节点，kube-scheduler 会从中随机选取一个。˜

支持以下两种方式配置调度器的过滤和打分行为：

  1. 调度策略 允许你配置过滤所用的 断言（Predicates） 和打分所用的 优先级（Priorities）。
  2. 调度配置 允许你配置实现不同调度阶段的插件， 包括：QueueSort、Filter、Score、Bind、Reserve、Permit 等等。 你也可以配置 kube-scheduler 运行不同的配置文件。

将 Pod 指派给节点

你可以约束一个 Pod 以便限制其只能在特定的节点上运行， 或优先在特定的节点上运行。有几种方法可以实现这点， 推荐的方法都是用标签选择算符来进行选择。 通常这样的约束不是必须的，因为调度器将自动进行合理的放置（比如，将 Pod 分散到节点上， 而不是将 Pod 放置在可用资源不足的节点上等等）。但在某些情况下，你可能需要进一步控制 Pod 被部署到哪个节点。例如，确保 Pod 最终落在连接了 SSD 的机器上， 或者将来自两个不同的服务且有大量通信的 Pod 被放置在同一个可用区。

node亲和力：

节点亲和性概念上类似于 nodeSelector， 它使你可以根据节点上的标签来约束 Pod 可以调度到哪些节点上。 节点亲和性有两种：

  • requiredDuringSchedulingIgnoredDuringExecution： 调度器只有在规则被满足的时候才能执行调度。此功能类似于 nodeSelector， 但其语法表达能力更强。
  • preferredDuringSchedulingIgnoredDuringExecution： 调度器会尝试寻找满足对应规则的节点。如果找不到匹配的节点，调度器仍然会调度该 Pod。

代码示例：

apiVersion: v1
kind: Pod
metadata:
  name: with-node-affinity
spec:
# 定义亲和力
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: kubernetes.io/hostname
            operator: In
            values:
            - master
            - work04
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1
        preference:
          matchExpressions:
          - key: kubernetes.io/hostname
            operator: In
            values:
            - work04
  containers:
  - name: with-node-affinity
    image: nginx:latest

在这一示例中，所应用的规则如下：

  • 节点必须包含一个键名为 topology.kubernetes.io/zone 的标签， 并且该标签的取值必须为 antarctica-east1 或 antarctica-west1。
  • 节点最好具有一个键名为 another-node-label-key 且取值为 another-node-label-value 的标签。

你可以使用 operator 字段来为 Kubernetes 设置在解释规则时要使用的逻辑操作符。 你可以使用 In、NotIn、Exists、DoesNotExist、Gt 和 Lt 之一作为操作符。

操作符

下面是你可以在上述 nodeAffinity 和 podAffinity 的 operator 字段中可以使用的所有逻辑运算符。

操作符 行为
In 标签值存在于提供的字符串集中
NotIn 标签值不包含在提供的字符串集中
Exists 对象上存在具有此键的标签
DoesNotExist 对象上不存在具有此键的标签

以下操作符只能与 nodeAffinity 一起使用。

操作符 行为
Gt 字段值将被解析为整数，并且该整数小于通过解析此选择算符命名的标签的值所得到的整数
Lt 字段值将被解析为整数，并且该整数大于通过解析此选择算符命名的标签的值所得到的整数

说明：

Gt 和 Lt 操作符不能与非整数值一起使用。 如果给定的值未解析为整数，则该 Pod 将无法被调度。 另外，Gt 和 Lt 不适用于 podAffinity。

调度策略

在 Kubernetes v1.23 版本之前，可以使用调度策略来指定 predicates 和 priorities 进程。 例如，可以通过运行 kube-scheduler --policy-config-file <filename> 或者 kube-scheduler --policy-configmap <ConfigMap> 设置调度策略。

但是从 Kubernetes v1.23 版本开始，不再支持这种调度策略。 同样地也不支持相关的 policy-config-file、policy-configmap、policy-configmap-namespace 和 use-legacy-policy-config 标志。 你可以通过使用调度配置来实现类似的行为。

污点和容忍度

节点亲和性 是 Pod 的一种属性，它使 Pod 被吸引到一类特定的节点 （这可能出于一种偏好，也可能是硬性要求）。 污点（Taint） 则相反——它使节点能够排斥一类特定的 Pod。

容忍度（Toleration） 是应用于 Pod 上的。容忍度允许调度器调度带有对应污点的 Pod。 容忍度允许调度但并不保证调度：作为其功能的一部分， 调度器也会评估其他参数。

污点和容忍度（Toleration）相互配合，可以用来避免 Pod 被分配到不合适的节点上。 每个节点上都可以应用一个或多个污点，这表示对于那些不能容忍这些污点的 Pod， 是不会被该节点接受的。

常用命令： kubectl taint

增加污点

[root@master 亲和力]# kubectl  taint  node  workd03 a=test:NoSchedule

去除污点

kubectl taint nodes workd03 a=test:NoSchedule-

容忍度：

tolerations:
- key: "污点的key"          # 匹配污点的键（如 "dedicated"）
  operator: "Equal"或"Exists"  # 匹配方式（等于/存在）
  value: "污点的value"      # 当 operator 为 Equal 时需指定，匹配污点的值
  effect: "NoSchedule"或"NoExecute"或"PreferNoSchedule"  # 匹配污点的效果
  tolerationSeconds: 300    # 仅对 NoExecute 有效，Pod 被驱逐前的宽限期（秒）

effect：匹配污点的效果

污点的 effect 决定了对 Pod 的排斥行为，容忍策略需指定对应的 effect 才能匹配。常见 effect 及容忍逻辑：

污点 effect 含义（节点对未容忍 Pod 的行为） 容忍后 Pod 的行为
NoSchedule 禁止新 Pod 调度到节点（已运行的 Pod 不受影响） 允许新 Pod 调度到节点
PreferNoSchedule 尽量不调度新 Pod 到节点（非强制，调度器会优先选择无此污点的节点） 调度器可将 Pod 调度到节点（无强制限制）
NoExecute 立即驱逐节点上已运行的未容忍 Pod，且禁止新 Pod 调度（最严格） 允许 Pod 调度到节点，且已运行的 Pod 不会被驱逐

operator 的默认值是 Equal。

一个容忍度和一个污点相“匹配”是指它们有一样的键名和效果，并且：

  • 如果 operator 是 Exists（此时容忍度不能指定 value），或者
  • 如果 operator 是 Equal，则它们的值应该相等。

effect 使用的值为 NoSchedule，你也可以使用另外一个值 PreferNoSchedule。

effect 字段的允许值包括：

  • NoExecute

这会影响已在节点上运行的 Pod，具体影响如下：如果 Pod 不能容忍这类污点，会马上被驱逐。如果 Pod 能够容忍这类污点，但是在容忍度定义中没有指定 tolerationSeconds， 则 Pod 还会一直在这个节点上运行。如果 Pod 能够容忍这类污点，而且指定了 tolerationSeconds， 则 Pod 还能在这个节点上继续运行这个指定的时间长度。 这段时间过去后，节点生命周期控制器从节点驱除这些 Pod。

  • NoSchedule

除非具有匹配的容忍度规约，否则新的 Pod 不会被调度到带有污点的节点上。 当前正在节点上运行的 Pod 不会被驱逐。

  • PreferNoSchedule

PreferNoSchedule 是“偏好”或“软性”的 NoSchedule。 控制平面将尝试避免将不能容忍污点的 Pod 调度到的节点上，但不能保证完全避免。

# 定义 Pod 的 API 版本和资源类型（固定为 v1 和 Pod）
apiVersion: v1
kind: Pod
metadata:
  name: with-node-affinity-totaint  # Pod 的名称，用于标识该资源

    effect: "NoSchedule"  # 匹配的污点效果（仅容忍效果为 NoSchedule 的污点）
    # 含义：允许 Pod 调度到带有污点 key=a、effect=NoSchedule 的节点（无论该污点的 value 是什么）

需求： 根据不同环境发布pod

dev prod

以下是为 开发环境（dev） 和 生产环境（prod） 分别创建 Nginx Pod 及对应的 ConfigMap 的完整配置，实现不同环境下 Nginx 配置的隔离与切换。

场景说明

  • 开发环境（dev）：Nginx 监听 8080 端口，显示开发环境标识页面。
  • 生产环境（prod）：Nginx 监听 80 端口（标准端口），显示生产环境标识页面，且配置更严格（如关闭目录浏览）。

步骤 1：创建命名空间（隔离环境）

先为两个环境创建独立的命名空间（避免资源冲突）：

# 创建开发环境命名空间
kubectl create namespace dev

# 创建生产环境命名空间
kubectl create namespace prod

步骤 2：创建环境专属的 ConfigMap

为 dev 和 prod 环境分别定义 ConfigMap，存储各自的 Nginx 配置文件和首页内容。

2.1 开发环境 ConfigMap（dev 命名空间）

# configmap-nginx-dev.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config  # 同名 ConfigMap，通过命名空间隔离
  namespace: dev      # 开发环境命名空间
data:
  # Nginx 配置文件（键为文件名，值为配置内容）
  default.conf: |
    server {
      listen 8080;  # 开发环境用 8080 端口
      server_name localhost;
      root /usr/share/nginx/html;
      index index.html;

      # 开发环境允许目录浏览（方便调试）
      autoindex on;
    }

  # 首页内容（区分环境标识）
  index.html: |
    <html>
      <head><title>Dev Environment</title></head>
      <body><h1>Welcome to Development Environment (dev)</h1></body>
    </html>

创建开发环境 ConfigMap：

kubectl apply -f configmap-nginx-dev.yaml

# configmap-nginx-prod.yaml

包管理器

kubernetes 的包管理器

Helm 是 Kubernetes 生态中最核心的包管理器，它能将 Kubernetes 应用的所有资源（如 Deployment、Service、ConfigMap 等）打包成统一的 “Chart”，实现应用的快速部署、版本管理、升级与回滚，极大简化了 K8s 应用的运维流程。

一、Helm 的核心价值：解决 K8s 应用管理痛点

在没有 Helm 时，部署一个复杂 K8s 应用（如 Nginx + MySQL + Redis）需要手动编写多个 YAML 文件，存在以下问题：

  1. 资源分散：一个应用对应多个 YAML（Deployment、Service 等），管理和分发困难；
  2. 版本混乱：应用升级 / 回滚时，需手动修改多个 YAML 版本，易出错；
  3. 环境适配差：开发 / 测试 / 生产环境的配置（如数据库地址、资源配额）需手动替换，效率低。

Helm 通过以下特性解决这些问题：

  • Chart 打包：将应用所有资源和配置模板打包成 “Chart”，可跨集群复用；
  • 版本控制：为每个应用版本生成 “Release”（部署实例），支持一键升级、回滚；
  • 配置模板化：通过 “Values.yaml” 分离配置与模板，支持不同环境动态注入配置（如 --set env=prod）。

二、Helm 的核心概念

Helm 3 之后移除了中心化的 “Tiller” 组件，架构更轻量，核心概念有 3 个：

概念 含义
Chart 应用的 “安装包”，包含应用的所有 K8s 资源模板（YAML）和配置模板（Values.yaml），可存储在本地或远程仓库（如 Helm Hub）。
Release Chart 部署到 K8s 集群后的 “实例”，每个 Chart 可多次部署（如部署 nginx-dev 和 nginx-prod 两个 Release），每个 Release 有独立版本。
Repository Chart 的 “仓库”，用于存储和分发 Chart（类似 Docker Hub），支持公开仓库（如 Artifact Hub）或私有仓库。

Network Policies 网络策略

Kubernetes Network Policies（网络策略） 是用于控制集群内 Pod 间网络流量的 API 资源，支持通过标签（Label）精准定义 “允许哪些 Pod 与哪些 Pod 通信”，默认拒绝所有未授权流量，可实现微服务间的网络隔离与安全访问控制。

一、核心概念与默认行为

  1. 核心作用
  2. 仅允许 “明确授权” 的 Pod 间通信，拒绝所有未匹配规则的流量（入站 / 出站）。
  3. 基于 Pod 标签（Pod Selector） 和 命名空间标签（Namespace Selector） 筛选流量源 / 目标，支持按端口、协议（TCP/UDP/SCTP）细化规则。
  4. 默认行为
  5. 若未创建任何 Network Policy，集群内所有 Pod 可自由通信（无网络隔离）。
  6. 一旦为某命名空间或 Pod 配置 Network Policy，仅匹配规则的流量会被允许，其余流量默认拒绝。
  7. 依赖条件
  8. 需 Kubernetes 网络插件支持（如 Calico、Flannel（需额外配置）、Cilium 等），纯原生 kube-proxy 不支持 Network Policies。

二、Network Policy 关键字段解析

以一个 “允许 frontend 命名空间的 Pod 访问 backend 命名空间 app=db 的 Pod 的 3306 端口” 的规则为例，核心字段如下：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-db-policy
  namespace: backend  # 策略作用的命名空间（仅对该命名空间内的 Pod 生效）
spec:
  podSelector:  # 目标 Pod 筛选（策略保护的 Pod）
    matchLabels:
      app: db  # 仅对标签为 app=db 的 Pod 生效
  policyTypes:  # 策略类型：Ingress（入站流量）、Egress（出站流量），可同时配置
  - Ingress
  ingress:  # 入站流量规则（允许哪些源访问目标 Pod）
  - from:  # 流量来源（支持多源配置）
    - namespaceSelector:  # 按命名空间筛选来源
        matchLabels:
          env: frontend  # 仅允许标签为 env=frontend 的命名空间的 Pod
    - podSelector:  # 按 Pod 标签筛选来源（可选，与 namespaceSelector 组合为“且”关系）
        matchLabels:
          role: api  # 进一步限制来源 Pod 需带 role=api 标签
    ports:  # 允许访问的端口与协议（仅允许 3306 端口的 TCP 流量）
    - protocol: TCP
      port: 3306

关键字段说明：

字段 作用
podSelector 定义策略作用的目标 Pod（必须配置，筛选当前命名空间内的 Pod）。若为空（matchLabels: {}），则对命名空间内所有 Pod 生效。
policyTypes 声明策略控制的流量方向：Ingress（入站，外部访问目标 Pod）、Egress（出站，目标 Pod 访问外部），至少配置一种。
ingress[].from 定义允许的入站流量来源，支持 3 种来源：- namespaceSelector：来自特定标签的命名空间的所有 Pod；- podSelector：来自当前命名空间内特定标签的 Pod；- ipBlock：来自特定 IP 段（如 cidr: 192.168.1.0/24）的流量。
ingress[].ports 定义允许入站流量访问的端口和协议（若不配置，允许所有端口）。
egress[].to / egress[].ports 与 ingress 对应，控制目标 Pod 的出站流量（允许访问哪些外部目标、哪些端口）。

三、常见 Network Policy 场景示例

根据实际需求，可配置不同场景的网络策略，以下为 3 个典型案例：

场景 1：拒绝所有入站流量（默认拒绝）

对某命名空间内的所有 Pod 禁用入站流量（仅允许 Pod 自身的出站流量，如访问外部服务）：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: backend
spec:
  podSelector: {}  # 作用于命名空间内所有 Pod
  policyTypes:
  - Ingress  # 仅控制入站流量，未配置 ingress.from 则默认拒绝所有入站

场景 2：允许特定 Pod 间的双向通信

允许 app=frontend 的 Pod 与 app=backend 的 Pod 互相访问（双向流量）：

# 1. 允许 backend 接收 frontend 的入站流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-frontend
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend  # 允许同一命名空间内 app=frontend 的 Pod 访问

# 2. 允许 frontend 接收 backend 的入站流量（若需双向）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frontend-allow-backend
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: backend

场景 3：限制 Pod 出站流量（仅允许访问特定服务）

控制 app=web 的 Pod 仅能访问 app=api 的 8080 端口和外部 192.168.1.0/24 网段：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-egress-policy
  namespace: frontend
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
  - Egress  # 控制出站流量
  egress:
  # 允许访问同一命名空间内 app=api 的 8080 端口
  - to:
    - podSelector:
        matchLabels:
          app: api
    ports:
    - protocol: TCP
      port: 8080
  # 允许访问外部 192.168.1.0/24 网段（如本地数据库）
  - to:
    - ipBlock:
        cidr: 192.168.1.0/24

四、策略优先级与生效逻辑

  1. 多策略叠加

若多个 Network Policy 作用于同一个 Pod，所有允许规则会 “叠加”（即满足任一策略的允许条件，流量就会被放行），但只要有一个策略明确拒绝（通过 ipBlock 排除），则流量被拒绝。

  1. 命名空间隔离

策略仅对其所在的命名空间内的 Pod 生效，无法直接控制跨命名空间的 Pod 策略（需通过 namespaceSelector 引用其他命名空间）。

  1. 流量方向独立

Ingress 和 Egress 规则独立生效，例如：可允许 Pod 接收所有入站流量，但仅允许其访问特定外部服务（限制出站）。

六、注意事项

  1. 网络插件兼容性

确保使用的网络插件支持 Network Policies（如 Calico、Cilium、Weave Net），避免使用仅支持基础网络的插件（如原生 Flannel）。

  1. 默认拒绝的风险

配置 default-deny-ingress 或 default-deny-egress 时，需确保已为必要的流量（如 DNS 解析、监控采集）配置允许规则，避免服务不可用。

  1. 标签管理

策略依赖 Pod / 命名空间标签，需确保标签定义清晰且不频繁变动，避免因标签修改导致策略失效。

Network Policies 是 Kubernetes 集群网络安全的核心工具，通过精细化的规则配置，可有效隔离不同服务的流量，降低跨服务攻击风险。若需针对特定场景（如跨命名空间访问、IP 段限制）配置策略，可以补充需求，我会提供更具体的示例。

Prometheus 是一个开源的系统监控和告警工具包，最初由 SoundCloud 公司开发。自 2012 年成立以来，许多公司和组织都采用了 Prometheus，该项目有一个非常活跃的开发者和用户社区。现在它已经是一个独立的开源项目，并且独立于任何公司进行维护。为了强调这一点，并澄清项目的治理结构，Prometheus 在 2016 年加入 Cloud Native Computing Foundation，成为继 Kubernetes 之后的第二个托管项目。

功能

Prometheus 的主要功能是:

  • 多维数据模型，时间序列数据通过指标名称和键/值对进行标识
  • PromQL，一种灵活的查询语言，利用这种多维性
  • 没有依赖分布式存储；单服务器节点是自治的
  • 时间序列收集是通过 HTTP 拉取模型进行的
  • 支持通过中间网关推送时间序列
  • 目标是通过服务发现或静态配置来发现的
  • 支持多种绘图和仪表板模式

这意味着 kubelet 配置必须包含这些标志：

  • --authentication-token-webhook=true This flag enables, that a ServiceAccount token can be used to authenticate against the kubelet(s). This can also be enabled by setting the kubelet configuration value authentication.webhook.enabled to true.
    --authentication-token-webhook=true 此标志启用 token 可以用于对 kubelet 进行认证。也可以通过将 kubelet 配置值 ServiceAccount 设置为 authentication.webhook.enabled 来启用。
  • --authorization-mode=Webhook This flag enables, that the kubelet will perform an RBAC request with the API to determine, whether the requesting entity (Prometheus in this case) is allowed to access a resource, in specific for this project the /metrics endpoint. This can also be enabled by setting the kubelet configuration value authorization.mode to Webhook.
    --authorization-mode=Webhook 此标志启用 kubelet 将向 API 发送一个 RBAC 请求，以确定请求实体（在这种情况下为 Prometheus）是否被允许访问资源，对于这个项目来说，是 /metrics 端点。也可以通过将 kubelet 配置值 authorization.mode 设置为 Webhook 来启用。
