网络策略 Prometheus

Network Policies 网络策略

Kubernetes Network Policies（网络策略） 是用于控制集群内 Pod 间网络流量的 API 资源，支持通过标签（Label）精准定义 “允许哪些 Pod 与哪些 Pod 通信”，默认拒绝所有未授权流量，可实现微服务间的网络隔离与安全访问控制。

一、核心概念与默认行为

  1. 核心作用
  2. 仅允许 “明确授权” 的 Pod 间通信，拒绝所有未匹配规则的流量（入站 / 出站）。
  3. 基于 Pod 标签（Pod Selector） 和 命名空间标签（Namespace Selector） 筛选流量源 / 目标，支持按端口、协议（TCP/UDP/SCTP）细化规则。
  4. 默认行为
  5. 若未创建任何 Network Policy，集群内所有 Pod 可自由通信（无网络隔离）。
  6. 一旦为某命名空间或 Pod 配置 Network Policy，仅匹配规则的流量会被允许，其余流量默认拒绝。
  7. 依赖条件
  8. 需 Kubernetes 网络插件支持（如 Calico、Flannel（需额外配置）、Cilium 等），纯原生 kube-proxy 不支持 Network Policies。

二、Network Policy 关键字段解析

以一个 “允许 frontend 命名空间的 Pod 访问 backend 命名空间 app=db 的 Pod 的 3306 端口” 的规则为例，核心字段如下：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-db-policy
  namespace: backend  # 策略作用的命名空间（仅对该命名空间内的 Pod 生效）
spec:
  podSelector:  # 目标 Pod 筛选（策略保护的 Pod）
    matchLabels:
      app: db  # 仅对标签为 app=db 的 Pod 生效
  policyTypes:  # 策略类型：Ingress（入站流量）、Egress（出站流量），可同时配置
  - Ingress
  ingress:  # 入站流量规则（允许哪些源访问目标 Pod）
  - from:  # 流量来源（支持多源配置）
    - namespaceSelector:  # 按命名空间筛选来源
        matchLabels:
          env: frontend  # 仅允许标签为 env=frontend 的命名空间的 Pod
    - podSelector:  # 按 Pod 标签筛选来源（可选，与 namespaceSelector 组合为“且”关系）
        matchLabels:
          role: api  # 进一步限制来源 Pod 需带 role=api 标签
    ports:  # 允许访问的端口与协议（仅允许 3306 端口的 TCP 流量）
    - protocol: TCP
      port: 3306

关键字段说明：

字段 作用
podSelector 定义策略作用的目标 Pod（必须配置，筛选当前命名空间内的 Pod）。若为空（matchLabels: {}），则对命名空间内所有 Pod 生效。
policyTypes 声明策略控制的流量方向：Ingress（入站，外部访问目标 Pod）、Egress（出站，目标 Pod 访问外部），至少配置一种。
ingress[].from 定义允许的入站流量来源，支持 3 种来源：- namespaceSelector：来自特定标签的命名空间的所有 Pod；- podSelector：来自当前命名空间内特定标签的 Pod；- ipBlock：来自特定 IP 段（如 cidr: 192.168.1.0/24）的流量。
ingress[].ports 定义允许入站流量访问的端口和协议（若不配置，允许所有端口）。
egress[].to / egress[].ports 与 ingress 对应，控制目标 Pod 的出站流量（允许访问哪些外部目标、哪些端口）。

三、常见 Network Policy 场景示例

根据实际需求，可配置不同场景的网络策略，以下为 3 个典型案例：

场景 1：拒绝所有入站流量（默认拒绝）

对某命名空间内的所有 Pod 禁用入站流量（仅允许 Pod 自身的出站流量，如访问外部服务）：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: backend
spec:
  podSelector: {}  # 作用于命名空间内所有 Pod
  policyTypes:
  - Ingress  # 仅控制入站流量，未配置 ingress.from 则默认拒绝所有入站

场景 2：允许特定 Pod 间的双向通信

允许 app=frontend 的 Pod 与 app=backend 的 Pod 互相访问（双向流量）：

# 1. 允许 backend 接收 frontend 的入站流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-frontend
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend  # 允许同一命名空间内 app=frontend 的 Pod 访问

# 2. 允许 frontend 接收 backend 的入站流量（若需双向）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frontend-allow-backend
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: frontend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: backend

场景 3：限制 Pod 出站流量（仅允许访问特定服务）

控制 app=web 的 Pod 仅能访问 app=api 的 8080 端口和外部 192.168.1.0/24 网段：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-egress-policy
  namespace: frontend
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
  - Egress  # 控制出站流量
  egress:
  # 允许访问同一命名空间内 app=api 的 8080 端口
  - to:
    - podSelector:
        matchLabels:
          app: api
    ports:
    - protocol: TCP
      port: 8080
  # 允许访问外部 192.168.1.0/24 网段（如本地数据库）
  - to:
    - ipBlock:
        cidr: 192.168.1.0/24

四、策略优先级与生效逻辑

  1. 多策略叠加

若多个 Network Policy 作用于同一个 Pod，所有允许规则会 “叠加”（即满足任一策略的允许条件，流量就会被放行），但只要有一个策略明确拒绝（通过 ipBlock 排除），则流量被拒绝。

  1. 命名空间隔离

策略仅对其所在的命名空间内的 Pod 生效，无法直接控制跨命名空间的 Pod 策略（需通过 namespaceSelector 引用其他命名空间）。

  1. 流量方向独立

Ingress 和 Egress 规则独立生效，例如：可允许 Pod 接收所有入站流量，但仅允许其访问特定外部服务（限制出站）。

五、验证与调试方法

  1. 查看网络策略
# 查看指定命名空间的所有 Network Policy
kubectl get networkpolicy -n backend
# 查看策略详情（含规则）
kubectl describe networkpolicy backend-db-policy -n backend
  1. 测试流量连通性

通过 kubectl exec 进入 Pod，使用 curl/ping 测试与目标 Pod 的通信，验证规则是否生效：

# 进入 frontend Pod，测试访问 backend 的 db Pod（3306 端口）
kubectl exec -it frontend-pod -n frontend -- curl -v backend-db-pod:3306
  1. 查看网络插件日志

若流量不符合预期，可查看网络插件日志（如 Calico）定位问题：

# 查看 Calico 节点日志（以 Calico 为例）
kubectl logs -n calico-system calico-node-xxxxxx

六、注意事项

  1. 网络插件兼容性

确保使用的网络插件支持 Network Policies（如 Calico、Cilium、Weave Net），避免使用仅支持基础网络的插件（如原生 Flannel）。

  1. 默认拒绝的风险

配置 default-deny-ingress 或 default-deny-egress 时，需确保已为必要的流量（如 DNS 解析、监控采集）配置允许规则，避免服务不可用。

  1. 标签管理

策略依赖 Pod / 命名空间标签，需确保标签定义清晰且不频繁变动，避免因标签修改导致策略失效。

Network Policies 是 Kubernetes 集群网络安全的核心工具，通过精细化的规则配置，可有效隔离不同服务的流量，降低跨服务攻击风险。若需针对特定场景（如跨命名空间访问、IP 段限制）配置策略，可以补充需求，我会提供更具体的示例。

案例： 监控系统 Prometheus

promethues 监控系统，为云原生而产生的应用

监控系统

  • 不是容器化的业务： zabbix 监控硬件，

  • 容器化的业务： Prometheus监控

链路追踪系统：

  • OpenTelemetry：当前的事实标准和未来趋势。它是一个 CNCF 毕业项目，提供了一套与供应商无关的 API、SDK 和工具，用于采集和导出遥测数据（链路、指标、日志）。它旨在统一之前的 OpenTracing 和 OpenCensus 两大标准。

  • Zipkin：由 Twitter 开发的开源先驱，简单易用，生态成熟。

  • Jaeger：由 Uber 开发并开源，是 CNCF 毕业项目。功能强大，支持高扩展性、多种存储后端和复杂的分布式场景。常与 OpenTelemetry 配合使用（OTel 采集，Jaeger 展示）。

日志监控系统：EL/FK

Prometheus 是一个开源的系统监控和告警工具包，最初由 SoundCloud 公司开发。自 2012 年成立以来，许多公司和组织都采用了 Prometheus，该项目有一个非常活跃的开发者和用户社区。现在它已经是一个独立的开源项目，并且独立于任何公司进行维护。为了强调这一点，并澄清项目的治理结构，Prometheus 在 2016 年加入 Cloud Native Computing Foundation，成为继 Kubernetes 之后的第二个托管项目。

功能

Prometheus 的主要功能是:

  • 多维数据模型，时间序列数据通过指标名称和键/值对进行标识
  • PromQL，一种灵活的查询语言，利用这种多维性
  • 没有依赖分布式存储；单服务器节点是自治的
  • 时间序列收集是通过 HTTP 拉取模型进行的
  • 支持通过中间网关推送时间序列
  • 目标是通过服务发现或静态配置来发现的
  • 支持多种绘图和仪表板模式

Prerequisites 前提条件

您将需要一个 Kubernetes 集群，就是这样！默认情况下假定 kubelet 使用 token 认证和授权，否则 Prometheus 需要一个客户端证书，这将赋予它对 kubelet 的完全访问权限，而不是仅仅是对指标的访问。token 认证和授权允许更精细和更简单的访问控制。

这意味着 kubelet 配置必须包含这些标志：

  • --authentication-token-webhook=true This flag enables, that a ServiceAccount token can be used to authenticate against the kubelet(s). This can also be enabled by setting the kubelet configuration value authentication.webhook.enabled to true.
    --authentication-token-webhook=true 此标志启用 token 可以用于对 kubelet 进行认证。也可以通过将 kubelet 配置值 ServiceAccount 设置为 authentication.webhook.enabled 来启用。
  • --authorization-mode=Webhook This flag enables, that the kubelet will perform an RBAC request with the API to determine, whether the requesting entity (Prometheus in this case) is allowed to access a resource, in specific for this project the /metrics endpoint. This can also be enabled by setting the kubelet configuration value authorization.mode to Webhook.
    --authorization-mode=Webhook 此标志启用 kubelet 将向 API 发送一个 RBAC 请求，以确定请求实体（在这种情况下为 Prometheus）是否被允许访问资源，对于这个项目来说，是 /metrics 端点。也可以通过将 kubelet 配置值 authorization.mode 设置为 Webhook 来启用。
