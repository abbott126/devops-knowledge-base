Pod 管理

Pod 管理

Pod 是kubernetes 中最小单元，Pod 容器

Pod 就是🫛，每一颗小豆豆称作为：container

Pod 是管理一个或者多个容器的单元；

Pod的语法：

apiVersion: v1   #api版本
kind: Pod        #k8s的对象资源类型 Pod
metadata:        #Pod的元数据
  name: nginx      #Pod 的名称 nginx
spec:            #定义规格
  containers:      #容器
  - name: nginx    #容器name 
    image: nginx:1.14.2    #镜像
    ports:         #端口号
    - containerPort: 80

Example: yaml

  1. 创建一个nginx的yaml文件

apiVersion: v1
kind: Pod
metadata:
  name: nginx

  containers:
  - name: nginx
    image: nginx:latest
  1. 创建nginx的Pod
[root@master Pod]# kubectl  create  -f  pod-example.yaml 
[root@master Pod]# kubectl  apply   -f  pod-example.yaml
  1. 查看pod 
[root@master Pod]# kubectl  get po  
NAME    READY   STATUS              RESTARTS   AGE
nginx   0/1     ContainerCreating   0          7m14s
  1. 看Pod的详细信息
[root@master Pod]# kubectl  describe pod nginx

Pod的生命周期

Pod 生命期

在 Pod 运行期间，kubelet 能够重启容器以处理一些失效场景。 在 Pod 内部，Kubernetes 跟踪不同容器的状态并确定使 Pod 重新变得健康所需要采取的动作。

Pod 在其生命周期中只会被调度一次。 将 Pod 分配到特定节点的过程称为绑定，而选择使用哪个节点的过程称为调度。 一旦 Pod 被调度并绑定到某个节点，Kubernetes 会尝试在该节点上运行 Pod。 Pod 会在该节点上运行，直到 Pod 停止或者被终止； 如果 Kubernetes 无法在选定的节点上启动 Pod（例如，如果节点在 Pod 启动前崩溃）， 那么特定的 Pod 将永远不会启动。

验证：可以通过删除原来的Pod

  1. 查看即将删除的Pod所在节点
语法： kubectl  describe  pod  {pod_name}
[root@master ~]# kubectl  describe po  nginx

删除pod

[root@master ~]# kubectl  delete  pods  nginx-init
pod "nginx-init" deleted
  1. 重新创建Pod 
[root@master ~]# kubectl  apply  -f  /opt/114-k8s-export/Pod/pod-init.yaml 
pod/nginx-init created

关联的生命周期

如果某物声称其生命期与某 Pod 相同，例如存储卷， 这就意味着该对象在此 Pod （UID 亦相同）存在期间也一直存在。 如果 Pod 因为任何原因被删除，甚至某完全相同的替代 Pod 被创建时， 这个相关的对象（例如这里的卷）也会被删除并重建。

Pod 阶段

Pod 的 status 字段是一个 PodStatus 对象，其中包含一个 phase 字段。

Pod 的阶段（Phase）是 Pod 在其生命周期中所处位置的简单宏观概述。 该阶段并不是对容器或 Pod 状态的综合汇总，也不是为了成为完整的状态机。

Pod 阶段的数量和含义是严格定义的。 除了本文档中列举的内容外，不应该再假定 Pod 有其他的 phase 值。

容器运行状态

Kubernetes 会跟踪 Pod 中每个容器的状态，就像它跟踪 Pod 总体上的阶段一样。 你可以使用容器生命周期回调 来在容器生命周期中的特定时间点触发事件。

一旦调度器将 Pod 分派给某个节点，kubelet 就通过容器运行时开始为 Pod 创建容器。容器的状态有三种：Waiting（等待）、Running（运行中）和 Terminated（已终止）。

要检查 Pod 中容器的状态，你可以使用 kubectl describe pod <pod 名称>。 其输出中包含 Pod 中每个容器的状态。

每种状态都有特定的含义：

Waiting（等待）

如果容器并不处在 Running 或 Terminated 状态之一，它就处在 Waiting 状态。 处于 Waiting 状态的容器仍在运行它完成启动所需要的操作：例如， 从某个容器镜像仓库拉取容器镜像，或者向容器应用 Secret 数据等等。 当你使用 kubectl 来查询包含 Waiting 状态的容器的 Pod 时，你也会看到一个 Reason 字段，其中给出了容器处于等待状态的原因。

!image-20251023153525241](/images/image-20251023153525241.png)

Running（运行中）

Running 状态表明容器正在执行状态并且没有问题发生。 如果配置了 postStart 回调，那么该回调已经执行且已完成。 如果你使用 kubectl 来查询包含 Running 状态的容器的 Pod 时， 你也会看到关于容器进入 Running 状态的信息。

Terminated（已终止）

处于 Terminated 状态的容器开始执行后，或者运行至正常结束或者因为某些原因失败。 如果你使用 kubectl 来查询包含 Terminated 状态的容器的 Pod 时， 你会看到容器进入此状态的原因、退出代码以及容器执行期间的起止时间。

  • Terminated（已终止）：表示资源已完全销毁，是最终状态；
  • Terminating（终止中）：是过渡状态，介于 “运行中” 和 “已终止” 之间。

如果容器配置了 preStop 回调，则该回调会在容器进入 Terminated 状态之前执行。

容器的重启策略

Pod 的 spec 中包含一个 restartPolicy 字段，其可能取值包括 Always、OnFailure 和 Never。默认值是 Always。

restartPolicy 应用于 Pod 中的应用容器和常规的 Init 容器。 Sidecar 容器忽略 Pod 级别的 restartPolicy 字段：在 Kubernetes 中，Sidecar 被定义为 initContainers 内的一个条目，其容器级别的 restartPolicy 被设置为 Always。 对于因错误而退出的 Init 容器，如果 Pod 级别 restartPolicy 为 OnFailure 或 Always， 则 kubelet 会重新启动 Init 容器。

  • Always：只要容器终止就自动重启容器。
  • OnFailure：只有在容器错误退出（退出状态非零）时才重新启动容器。
  • Never：不会自动重启已终止的容器

容器的拉取策略

容器的 imagePullPolicy 和镜像的标签会影响 kubelet 尝试拉取（下载）指定的镜像。

以下列表包含了 imagePullPolicy 可以设置的值，以及这些值的效果：

  • IfNotPresent

只有当镜像在本地不存在时才会拉取。

  • Always

每当 kubelet 启动一个容器时，kubelet 会查询容器的镜像仓库， 将名称解析为一个镜像摘要。 如果 kubelet 有一个容器镜像，并且对应的摘要已在本地缓存，kubelet 就会使用其缓存的镜像； 否则，kubelet 就会使用解析后的摘要拉取镜像，并使用该镜像来启动容器。

  • Never

kubelet 不会尝试获取镜像。如果镜像已经以某种方式存在本地， kubelet 会尝试启动容器；否则，会启动失败。 更多细节见提前拉取镜像。

容器探针Container probes

在 Kubernetes 中，容器探针（Container Probes） 是用于监控容器健康状态的机制，Kubernetes 通过探针定期检查容器的运行状态，根据检查结果决定是否重启容器或调整流量路由，以保证应用的可用性。

探针的类型

Kubernetes 提供三种类型的探针，分别用于不同场景：

1. 存活探针（Liveness Probe）

  • 作用：判断容器是否 “存活”（运行正常）。如果探测失败，kubelet 会杀死该容器，并根据容器的 restartPolicy（重启策略）决定是否决定是否重启。
  • 典型用场景：检测应用死锁（如进程进程存在但无法响应请求），通过重启容器恢复服务。

2. 就绪探针（Readiness Probe）

  • 作用：判断容器是否 “就绪”（可以接收请求）。如果探测失败，Pod 会被从 Service 的 endpoints 中移除，不再接收流量。
  • 典型场景：应用启动时需要加载配置或数据（启动慢），就绪探针确保仅当应用完全准备好后才接收请求。

3. 启动探针（Startup Probe，K8s 1.16+ 新增）

  • 作用：判断容器内的应用是否 “启动完成”。仅在启动探针成功后，存活探针和就绪探针才会开始工作。
  • 典型场景：针对启动缓慢的应用（如大型 JVM 服务），避免存活探针在启动过程中误判为故障而重启容器。

探针的检测方式

每种探针都支持三种检测方法，可根据应用特性选择：

1. HTTP 检测（HTTP GET）

  • 向容器的指定端口和路径发送 HTTP GET 请求，返回状态码 200-399 视为成功。
  • 示例：检查 Web 服务的 /health 接口是否可用。
    livenessProbe:
      httpGet:
        path: /var/www/html/index.html
        port: 80
      initialDelaySeconds: 5  ## 启动后5秒开始首次探测
      periodSeconds: 5  # 每5秒探测一次

2. 命令检测（Exec）

  • 在容器内执行指定命令，若命令退出码为 0 视为成功。
  • 示例：执行 cat /tmp/healthy 检查文件是否存在，存在则认为健康。
apiVersion: v1
kind: Pod
metadata:
  name: web-server
spec:
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80
    args:
    - /bin/sh
    - -c
    - |
      mkdir -p  /var/www/html/;
      echo  "hello world" >  /var/www/html/index.html;
      sleep  60;
      rm -rf  /var/www/html/index.html;
      nginx -g 'daemon off;'
     livenessProbe:
       exec:
         command:
         - ls
         - /var/www/html/index.html
       initialDelaySeconds: 5  ## 启动后5秒开始首次探测
       periodSeconds: 5  # 每5秒探测一次
  • args 作用：Nginx 镜像默认启动命令是 nginx -g 'daemon off;'，这里通过 args 覆盖为自定义脚本，目的是在启动时创建 /var/www/html/index.html 文件（内容为 hello world），后续 Nginx 会默认加载该目录下的页面。

3. TCP 检测（TCP Socket）

  • 尝试与容器的指定端口建立 TCP 连接，连接成功视为成功。
  • 示例：检查数据库服务的 8080 端口是否可连接。
    livenessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 5  ## 启动后5秒开始首次探测
      periodSeconds: 5  # 每5秒探测一次

探针的配置参数

探针的行为可通过以下参数精细化控制：

  • initialDelaySeconds：容器启动后，首次探测的延迟时间（秒，默认 0）。
  • periodSeconds：探测的间隔时间（秒，默认 10）。
  • timeoutSeconds：单次探测的超时时间（秒，默认 1）。
  • successThreshold：探测失败后，连续多少次成功才算 “成功”（默认 1）。
  • failureThreshold：探测成功后，连续多少次失败才算 “失败”（默认 3）。

名称空间 namespaces

在 Kubernetes（K8s）中，Namespace（命名空间） 是用于对集群内资源进行逻辑隔离和分组管理的核心概念。它本质上是一个 “资源隔离容器”，可以将集群中的 Pod、Service、Deployment 等资源划分到不同的命名空间中，实现多团队、多环境的资源隔离与权限控制。

一、Namespace 的核心作用

  1. 资源隔离：不同命名空间中的资源名称可以重复（如两个命名空间都可创建名为 nginx 的 Pod），避免全局资源命名冲突。
  2. 环境隔离：可按环境划分命名空间（如 dev 开发环境、test 测试环境、prod 生产环境），确保不同环境的资源独立，避免测试操作影响生产。
  3. 权限与配额控制：结合 RBAC（基于角色的访问控制）可限制用户仅能操作特定命名空间的资源；同时可通过 ResourceQuota 为每个命名空间设置资源上限（如最大 CPU / 内存使用量），防止单个团队过度占用集群资源。
  4. 简化资源管理：通过命名空间过滤资源，避免集群资源过多时的管理混乱（如仅查看生产环境资源，无需关注开发环境）。

二、Kubernetes 内置的默认命名空间

K8s 集群初始化时会自动创建 4 个核心命名空间，用于承载不同类型的资源：

  1. default：默认命名空间，未指定命名空间的资源会自动归属此处（适合临时测试或简单场景）。
  2. kube-system：用于存放 Kubernetes 核心组件（如 kube-apiserver、kube-scheduler、kube-proxy 等）和系统级插件（如网络插件、监控插件）的资源，禁止用户随意修改。
  3. kube-public：公共命名空间，所有用户（包括未授权用户）均可访问，通常用于存放集群级的公共配置（如集群信息 ConfigMap）。
  4. kube-node-lease：用于存放节点的租约信息，K8s 通过此处的资源判断节点是否存活（1.13+ 版本引入，优化节点心跳机制）。
[root@master 探针]# kubectl  get namespaces
NAME              STATUS   AGE
default           Active   2d4h
kube-node-lease   Active   2d4h
kube-public       Active   2d4h
kube-system       Active   2d4h

三、Namespace 的关键特性

  1. 命名空间的边界
  2. 隔离的资源：Pod、Service、Deployment、ConfigMap、Secret 等大部分核心资源。
  3. 不隔离的资源：Node（节点）、PersistentVolume（持久卷）等集群级资源（因为节点是物理 / 虚拟资源，PV 是全局共享的存储资源）。
  4. 跨命名空间访问：不同命名空间的资源可通过 “命名空间 + 资源名称” 的方式访问。例如，dev 命名空间的 Pod 要访问 prod 命名空间的 mysql Service，可通过 mysql.prod.svc.cluster.local（Service 的 DNS 格式：<service-name>.<namespace>.svc.<cluster-domain>）。
  5. 生命周期独立：删除命名空间时，会自动删除该命名空间下的所有资源（Pod、Service 等），但不会影响其他命名空间。

使用场景示例

  1. 多团队协作：团队 A 使用 team-a 命名空间，团队 B 使用 team-b 命名空间，通过 RBAC 配置仅允许各自团队操作自己的命名空间，避免误操作。
  2. 多环境部署：开发环境（dev）用于日常开发测试，测试环境（test）用于功能验证，生产环境（prod）用于线上服务，通过命名空间隔离确保环境稳定性。
  3. 资源配额控制：为 dev 命名空间设置 CPU 上限 4 核、内存上限 8GB，防止开发环境资源占用过多影响生产环境。

总结

Namespace 是 Kubernetes 中实现资源隔离与精细化管理的基础，通过合理划分命名空间，可有效提升集群的安全性、可维护性，适配多团队、多环境的复杂部署场景。实际使用中，建议避免使用 default 命名空间部署正式服务，而是根据业务需求规划专属命名空间。
