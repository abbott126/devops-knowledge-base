Kubernetes 网络

kubernetes Network

集群的网络

网络是Kubernetes的核心部分，但要准确理解它是如何工作的可能具有挑战性。有4个不同的网络问题需要解决：

  1. 高度耦合的容器到容器通信：这可以通过以下方式解决豆荚和localhost通信。
  2. Pod-to-Pod沟通：这是本文档的主要重点。
  3. Pod-to-Service通信：服务涵盖此项。
  4. 外部与服务之间的通信：服务部门也涵盖此信息。

Kubernetes就是关于在应用程序之间共享机器。通常，共享机器需要确保两个应用程序不会尝试使用相同的端口。跨多个开发人员的端口协调规模非常困难，并且会暴露用户无法控制的集群级问题。

动态端口分配给系统带来了很多复杂功能——每个应用程序都必须将端口作为标志，API服务器必须知道如何将动态端口号插入到配置块中，服务必须知道如何找到彼此，等等。Kubernetes没有处理这个问题，而是采取了不同的方法。

Kubernetes IP地址范围

Kubernetes集群需要从以下组件中配置的一系列可用地址中为Pod、服务和节点分配非重叠的IP地址：

  • 网络插件被配置为为Pods分配IP地址。
  • kube-apiserver被配置为为服务分配IP地址。
  • kubelet或云控制器管理器被配置为为为节点分配IP地址。

Cluster networking types

负责配置的 IP 系列的 Kubernetes 集群可分为：

  • 仅 IPv4：网络插件 kube-apiserver 和 kubelet/cloud-controller-manager 配置为仅分配 IPv4 地址。
  • 仅 IPv6：网络插件 kube-apiserver 和 kubelet/cloud-controller-manager 配置为仅分配 IPv6 地址。
  • IPv4/IPv6 或 IPv6/IPv4 双栈 ：
  • 网络插件配置为分配 IPv4 和 IPv6 地址。
  • kube-apiserver 配置为分配 IPv4 和 IPv6 地址。
  • kubelet 或 cloud-controller-manager 配置为分配 IPv4 和 IPv6 地址。
  • 所有组件都必须就配置的主 IP 系列达成一致。

Kubernetes 集群仅考虑 Pod、Services 和 Nodes 对象上存在的 IP 系列，独立于所表示对象的现有 IP。例如，服务器或 Pod 的接口上可以有多个 IP 地址，但只有 node.status.addresses或 pod.status.ips 中的 IP 地址才能考虑实现 Kubernetes 网络模型和定义集群类型。

Pod 网络

是 Kubernetes 集群中实现 Pod 间通信、以及 Pod 与集群内外资源通信的关键机制。每个 Pod 都会被分配一个独立的 IP 地址，使其能够像虚拟机一样，通过 IP 地址进行寻址和通信。

Pod 网络的核心原则

Kubernetes 的网络模型设计遵循以下基本原则：

  • IP-Per-Pod：集群中的每个 Pod 都有一个唯一的 IP 地址。
  • 无需 NAT：所有 Pod 之间都可以直接使用各自的 Pod IP 地址进行通信，无需进行网络地址转换（NAT），无论这些 Pod 是否位于同一节点上。
  • 节点通信：节点上的代理（如 Kubelet）可以与该节点上的所有 Pod 进行通信。

Pod 内部通信

在单个 Pod 内，所有容器共享同一个网络命名空间、IP 地址和端口空间。这意味着 Pod 中的不同容器可以直接通过 localhost 或 127.0.0.1 相互通信。

Pod 间通信

Pod 间的通信模式根据 Pod 是否在同一节点上而有所不同，但对 Pod 本身是透明的。

  • 同一节点内：位于同一节点上的 Pods 可以通过该节点上的虚拟网络桥接进行通信，延迟较低。
  • 不同节点间：位于不同节点上的 Pods 之间的通信，则由底层的网络解决方案（CNI 插件）创建的覆盖网络（overlay network）或路由机制来处理。CNI 插件负责确保即使 Pod 位于不同物理节点上，Pod IP 也能正常路由。

实现 Pod 网络模型

Kubernetes 本身不提供 Pod 网络功能，而是通过以下组件和机制来定义和实现网络要求：

  • CNI（容器网络接口）：CNI 是一种标准接口，定义了网络插件如何为 Pod 分配 IP 地址和配置网络。当创建 Pod 时，kubelet 会调用配置好的 CNI 插件来完成网络设置。
  • CNI 插件：实现了 CNI 标准的插件，负责具体的网络配置工作。常见的 CNI 插件包括：
  • Calico：提供强大的网络策略和网络安全功能。
  • Flannel：轻量级、易于部署的覆盖网络解决方案。
  • Weave Net：提供简便的跨主机容器网络。
  • Cilium：基于 eBPF 技术，提供高性能网络和安全策略。
  • IP 地址管理（IPAM）：作为 CNI 的一部分，IPAM 负责为 Pod 分配唯一的 IP 地址。通常，每个节点会被分配一个不重叠的 Pod IP 地址段，然后该节点上的 Pods 将从这个地址段中获取 IP 地址。

Pod 网络的局限性和服务

由于 Pod 是短暂的（当 Pod 被重新创建时，其 IP 地址会改变），直接依赖 Pod IP 进行通信是不稳定的。为了解决这个问题，Kubernetes 引入了 Service 抽象：

  • Service：为一组 Pod 提供一个稳定的 IP 地址和 DNS 名称。客户端只需通过 Service 的 IP 地址或 DNS 名称访问，Service 会负责将请求负载均衡到后端健康的 Pod 上，从而隐藏了 Pod IP 地址动态变化的细节。

总而言之，Pod 网络是 Kubernetes 平台实现容器互联互通的基础，它通过 CNI 插件为每个 Pod 提供唯一的 IP 地址，并通过 Service 机制提供稳定的访问入口，确保了分布式应用的高效通信。

ingress

帮助k8s实现暴露到外部的一个控制器；

在 Kubernetes 中，Ingress 是管理集群外部访问集群内服务（通常是 HTTP/HTTPS 流量）的 API 资源，它提供了路由规则、域名绑定、SSL 终止、负载均衡等功能，是集群外部流量进入内部服务的 “入口网关”。

为什么需要 Ingress？

Kubernetes 中的 Service 虽然能暴露服务，但存在局限：

  • NodePort 会占用节点端口，且暴露方式不友好（需用 节点IP:端口 访问）。
  • LoadBalancer 依赖云厂商，成本较高，且每个服务都需要独立的负载均衡器。

Ingress 解决了这些问题：

  • 统一管理所有 HTTP/HTTPS 流量的路由规则。
  • 支持基于域名、路径的精细化路由（例如将 api.example.com 路由到 API 服务，web.example.com 路由到 Web 服务）。
  • 集中配置 SSL 证书，实现 HTTPS 加密。
  • 无需为每个服务单独暴露端口，通过一个入口点管理所有服务。

Ingress 的核心组成

  1. Ingress 资源：通过 YAML 定义的路由规则（如域名、路径、后端服务等）。

  2. Ingress 控制器（Ingress Controller）

：实际执行路由规则的组件（如 Nginx、Traefik 等），是 Ingress 功能的 “执行者”。

注意：仅创建 Ingress 资源无效，必须先部署 Ingress 控制器，否则规则不会生效。

常见 Ingress 控制器

  • Nginx Ingress Controller：最常用，基于 Nginx 反向代理实现，支持丰富的配置。
  • Traefik：云原生网关，自动发现服务，配置简单，适合动态环境。
  • Cilium Ingress Controller 是由 Cilium 提供的 ingress controller。
  • HAProxy Ingress：基于 HAProxy，性能优秀，适合高并发场景。
  • Istio Ingress Gateway：服务网格 Istio 的入口组件，支持更复杂的流量治理（如熔断、限流）。

先决条件

需要满足条件：一个或者多个ingress

为了使 Ingress 资源工作，集群中必须运行一个 ingress 控制器

官方地址：https://kubernetes.github.io/ingress-nginx/deploy/#bare-metal-clusters

Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: minimal-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx-example
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        #定义后端service的字段
        backend:
          #后端service
          service:
            #service 名称
            name: test
            #service 端口
            port:
              number: 80

pathType

每个 Ingress 中的路径都需要对应一个路径类型。未包含显式 pathType 的路径将无法通过验证。支持三种路径类型：

ImplementationSpecific : 使用此路径类型时，匹配由 IngressClass 处理。

Exact : 精确匹配 URL 路径，并且区分大小写

Prefix : 根据 URL 路径的前缀进行匹配，前缀由 / 分割。匹配是区分大小写的，并且逐路径元素进行匹配。

实现LB

基于云厂商

纯软件解决方案：MetalLB

MetalLB 为不运行在受支持云提供商上的 Kubernetes 集群提供了网络负载均衡器实现，有效地允许在任何集群中使用 LoadBalancer 服务。

MetalLB 是专门为裸金属（Bare-metal）Kubernetes 集群设计的 LoadBalacer 实现，可解决本地集群（非云环境）中 Service 类型为 LoadBalancer 时无法分配外部 IP 的问题（云厂商通常通过自家 LB 服务自动分配 IP，本地集群无此能力）。

一、MetalLB 工作原理

MetalLB 会为集群中的 LoadBalancer 类型 Service 分配一个预配置的静态 IP 池中的 IP，并通过以下两种模式将 IP 暴露到集群外部：

  1. Layer 2 模式（二层模式）：通过 ARP/NDP 协议在本地局域网广播 IP 映射，使该 IP 与集群中某节点绑定（类似 “浮动 IP”），适合小型网络。
  2. BGP 模式（三层模式）：通过 BGP 协议与外部路由器通信，动态宣告 IP 路由，适合大规模网络或需要更高可用性的场景。

最常用的是 Layer 2 模式（配置简单，无需路由器支持）。

二、部署 MetalLB 步骤（以 Layer 2 模式为例）

  1. 前提条件

  2. Kubernetes 集群版本 ≥ v1.19（推荐 v1.24+）。

  3. 集群未启用云厂商的 LoadBalancer 控制器（如 GKE、EKS 自带的 LB，本地集群默认满足）。

  4. 准备一个未被局域网中其他设备占用的 IP 段（作为 MetalLB 的 IP 池，例如 192.168.1.200-192.168.1.210）。

  5. 安装 MetalLB

推荐用官方 Manifest 部署（适用于大多数集群）：

# 下载最新版本的部署文件（v0.13.10 为示例，可替换为最新版）
kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.13.10/config/manifests/metallb-native.yaml

# 验证部署（命名空间为 metallb-system）
kubectl get pods -n metallb-system
# 预期输出：controller 和 speaker  pods 运行中
# NAME                          READY   STATUS    RESTARTS   AGE
# metallb-controller-xxxxxx     1/1     Running   0          1m
# metallb-speaker-xxxxx         1/1     Running   0          1m
# metallb-speaker-yyyyy         1/1     Running   0          1m
  • controller：负责 IP 分配和管理 LoadBalancer Service。

  • speaker：运行在每个节点上，负责通过 ARP/BGP 广播 IP（DaemonSet 类型）。

  • 配置 IP 池（Layer 2 模式）

创建 IPAddressPool 和 L2Advertisement 资源，定义可用 IP 范围并启用二层广播：

# metallb-config.yaml
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: default-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.1.200-192.168.1.210  # 替换为你的局域网空闲 IP 段
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: l2-advert
  namespace: metallb-system
spec:
  ipAddressPools:
  - default-pool  # 关联上面定义的 IP 池

应用配置：

kubectl apply -f metallb-config.yaml
三、验证 MetalLB 功能

创建一个 LoadBalancer 类型的 Service，测试是否能自动分配 IP：

# test-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-test
spec:
  selector:
    app: nginx  # 假设已有标签为 app=nginx 的 Pod
  ports:
  - port: 80
    targetPort: 80
  type: LoadBalancer  # 关键：使用 LoadBalancer 类型

部署 Service 并查看：

kubectl apply -f test-service.yaml

# 查看 Service，关注 EXTERNAL-IP 字段
kubectl get svc nginx-test
# 预期输出（EXTERNAL-IP 会从 MetalLB 池中分配）：
# NAME         TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)        AGE
# nginx-test   LoadBalancer   10.96.xxx.xxx   192.168.1.200   80:32123/TCP   10s
  • 此时，外部设备（如本地电脑）可通过 192.168.1.200:80 访问该 Service，流量会被转发到后端 Pod。

四、关键配置说明

  1. IP 池规划

  2. IP 段必须在局域网网段内（如 192.168.1.0/24），且未被其他设备使用（避免 IP 冲突）。

  3. 可配置多个 IP 池（多个 IPAddressPool），并通过 L2Advertisement 关联不同池。

  4. 高可用（Layer 2 模式）

  5. Layer 2 模式下，MetalLB 会将 IP 绑定到集群中的一个节点（“领导者” 节点），若该节点故障，会自动漂移到其他节点（约 10-30 秒切换）。

  6. 需确保节点间网络互通，且防火墙允许 ARP 广播（否则 IP 漂移可能失败）。

  7. BGP 模式（可选）

若局域网有支持 BGP 的路由器（如 Cisco、Juniper），可配置 BGP 模式实现更灵活的路由控制（如跨子网访问），需额外定义 BGPPeer 资源关联路由器。

五、常见问题解决
  1. Service 一直处于 <pending> 状态
  2. 检查 MetalLB 组件是否正常运行：kubectl logs -n metallb-system <controller-pod>。
  3. 确认 IP 池配置正确（IP 段未被占用，且在局域网内）。
  4. 外部无法访问分配的 EXTERNAL-IP
  5. 检查节点防火墙是否开放 Service 对应的端口（Layer 2 模式下，流量会先到绑定 IP 的节点，再转发到 Pod）。
  6. 确认本地电脑与 EXTERNAL-IP 网段互通（如 ping 192.168.1.200 测试）。
  7. IP 冲突
  8. 确保 IP 池中的 IP 未被其他设备使用（可通过 arp-scan 工具扫描局域网 IP 占用情况）。
六、总结

MetalLB 是本地 Kubernetes 集群实现 LoadBalancer 类型 Service 的最佳方案，通过 Layer 2 模式可快速部署，解决外部 IP 分配问题。只需规划好 IP 池，即可让集群中的服务像云环境一样通过固定 IP 暴露，无需手动配置 NodePort 或第三方 LB。
