工作负载管理

工作负载管理 workload manager

在 Kubernetes（K8s）中，控制器（Controller） 是实现集群状态自动化管理的核心组件，它遵循 “声明式 API” 理念：用户通过 YAML 定义资源的 “期望状态”，控制器持续监控集群的 “实际状态”，并通过一系列操作将实际状态向期望状态推进。

简单来说，控制器就是 K8s 中的 “自动化运维工具”，负责 Pod 的创建、扩缩容、自愈、更新等核心操作，避免人工干预。

控制器的核心工作原理

  1. 监听状态：通过 API Server 实时监听目标资源（如 Pod、Deployment）的状态变化。
  2. 对比状态：将 “实际状态” 与用户定义的 “期望状态” 进行对比。
  3. 执行调和（Reconciliation）：若实际状态与期望状态不一致，控制器会触发一系列操作（如创建 Pod、删除异常实例、调整副本数），直到两者一致。

这个 “监听 - 对比 - 调和” 的循环，是所有 K8s 控制器的核心逻辑。

K8s 中常用的核心控制器

1. Deployment（部署控制器）

  • 核心作用：管理无状态应用，提供 Pod 的创建、扩缩容、滚动更新、回滚等功能，是最常用的控制器。
  • 关键特性
  • 支持设n，自动维持 Pod 数量（如 Pod 异常退出时自动重启）。
  • 滚动更新（Rolling Update）：逐步替换旧版本 Pod，确保服务不中断。
  • 回滚（Rollback）：若更新失败，可快速回滚到之前的稳定版本。
  • 适用场景：Web 服务、API 接口等无状态应用（无需持久化存储，实例可随意替换）。

2. StatefulSet（有状态集控制器）

  • 核心作用：管理有状态应用，解决 Deployment 无法满足的有状态场景需求。
  • 关键特性
  • 为每个 Pod 分配固定的名称（格式：<statefulset-name>-<ordinal-index>，如 mysql-0、mysql-1）和网络标识（通过 Headless Service 实现固定 DNS）。
  • 支持有序部署 / 删除（按序号从 0 到 N-1 启动，反向停止）。
  • 与 PersistentVolumeClaim（PVC）模板结合，为每个 Pod 分配独立的持久化存储（避免数据共享冲突）。
  • 适用场景：数据库（MySQL、PostgreSQL）、分布式存储（Elasticsearch、ZooKeeper）等需要固定标识和独立存储的应用。

3. DaemonSet（守护进程集控制器）

  • 核心作用：确保集群中所有（或指定）节点上都运行一个相同的 Pod 副本，类似传统的 “守护进程”。
  • 关键特性
  • 新节点加入集群时，自动在该节点上创建对应的 Pod；节点移除时，自动删除 Pod。
  • 支持通过节点选择器（nodeSelector）或亲和性规则，仅在特定节点上部署 Pod。
  • 适用场景：日志收集（Fluentd、Logstash）、监控代理（Prometheus Node Exporter）、网络插件（Calico、Flannel）等需要在每个节点上运行的服务。

4. ReplicaSet（副本集控制器）

  • 核心作用：确保集群中始终运行指定数量的 Pod 副本，是 Deployment 的底层依赖（Deployment 通过控制 ReplicaSet 实现副本管理）。
  • 关键特性：仅负责维持副本数，不支持滚动更新、回滚等高级功能。
  • 注意：实际使用中，优先选择 Deployment 而非直接使用 ReplicaSet，因为 Deployment 提供了更完整的生命周期管理能力。

5. Job（任务控制器）

  • 核心作用：管理一次性任务（批处理任务），确保任务执行完成后终止 Pod。
  • 关键特性
  • 任务成功完成后，Pod 状态变为 Succeeded，不再重启。
  • 支持并行执行多个任务（通过 parallelism 配置并行数）。
  • 适用场景：数据备份、批量计算、一次性脚本执行等短期任务。

6. CronJob（定时任务控制器）

  • 核心作用：管理周期性执行的任务，类似 Linux 中的 crontab。
  • 关键特性
  • 通过 schedule 字段定义执行周期（如 0 3 * * * 表示每天凌晨 3 点执行）。
  • 支持配置任务超时时间、失败重试策略等。
  • 适用场景：定时数据清理、定时报表生成、定时备份等周期性任务。

7. HorizontalPodAutoscaler（HPA，水平 Pod 自动扩缩容控制器）

  • 核心作用：根据 Pod 的 CPU / 内存使用率或自定义指标（如请求量），自动调整控制器（Deployment、StatefulSet 等）的副本数，实现弹性伸缩。
  • 关键特性
  • 支持设置最小副本数和最大副本数，避免扩缩容过度。
  • 可结合监控系统（如 Prometheus）获取自定义指标。
  • 适用场景：流量波动较大的应用（如电商促销期间自动扩容，低峰期自动缩容，节省资源）。

控制器与 Pod 的关系

  • 控制器不直接管理 Pod，而是通过 “控制循环” 间接操作：用户定义控制器的期望状态（如 Deployment 的 replicas: 3），控制器根据该状态创建 / 删除 Pod，或调整 Pod 的数量。
  • Pod 是控制器的 “被管理对象”，控制器确保 Pod 的状态始终符合期望。例如，Deployment 管理的 Pod 若因节点故障被删除，Deployment 会立即在其他健康节点上创建新的 Pod 以维持副本数。

总结

K8s 控制器的核心价值是 “自动化运维”，通过不同类型的控制器，可满足无状态、有状态、守护进程、定时任务等多种业务场景的需求。实际使用中，需根据应用的特性选择合适的控制器：

  • 无状态应用 → Deployment
  • 有状态应用 → StatefulSet
  • 节点级服务 → DaemonSet
  • 一次性任务 → Job
  • 定时任务 → CronJob
  • 弹性伸缩 → HPA

Deployment（部署控制器）

常用命令：

rollout：管理资源的滚动更新（如 Deployment 的版本升级、回滚等操作）

scale：为 Deployment（部署控制器）、ReplicaSet（副本集）或 Replication Controller（复制控制器）设置新的副本数量（即调整资源的实例规模）

autoscale：为 Deployment、ReplicaSet、StatefulSet（有状态集）或 Replication Controller 配置自动扩缩容（根据 CPU 使用率、自定义指标等自动调整副本数）

示例：

# apiVersion：指定 Kubernetes API 版本，Deployment 属于 apps 组，版本为 v1
apiVersion: apps/v1
# kind：定义资源类型，这里是 Deployment（部署控制器）
kind: Deployment
# metadata：资源的元数据，用于标识和描述 Deployment
metadata:
  name: nginx-deployment  # Deployment 的名称（唯一标识）
  labels:  # 给 Deployment 自身打的标签（用于分类或关联其他资源）
    app: nginx  # 标签键值对，键为 app，值为 nginx
# spec：Deployment 的核心配置，定义期望状态
spec:
  # replicas：期望运行的 Pod 副本数（控制器会自动维持这个数量）
  replicas: 3
  # selector：选择器，用于关联被管理的 Pod（通过标签匹配）
  selector:
    matchLabels:  # 匹配标签：仅管理带有 app: nginx 标签的 Pod
      app: nginx
  # template：Pod 模板，定义要创建的 Pod 的规格（Deployment 根据此模板生成 Pod）
  template:
    # metadata：Pod 的元数据
    metadata:
      labels:  # 给 Pod 打的标签（必须与上面的 selector.matchLabels 匹配，否则无法被管理）
        app: nginx
    # spec：Pod 的具体配置（包含容器信息）
    spec:
      # containers：Pod 中运行的容器列表（这里只有一个 Nginx 容器）
      containers:
      - name: nginx  # 容器名称（在 Pod 内唯一）
        image: nginx:1.14.2  # 容器使用的镜像（Nginx 1.14.2 版本）
        ports:  # 容器暴露的端口（仅用于标识，不自动映射到宿主机）
        - containerPort: 80  # 容器内 Nginx 实际监听的端口（默认 80）

扩/缩容 Scaling a Deployment

手动扩容：

[root@master deployment]# kubectl  scale   --replicas=5  deployment/nginx-deployment

缩容：

ter deployment]# kubectl  scale --replicas=1 deployment/nginx-deployment
deployment.apps/nginx-deployment scaled

更新策略

strategy:  # 定义 Deployment 的更新策略（控制如何替换旧版本 Pod）
  rollingUpdate:  # 滚动更新的具体参数配置
    maxSurge: 25%  # 允许超出期望副本数的最大比例（或绝对值）
                   # 含义：更新过程中，集群中同时运行的 Pod 总数最多比期望副本数（replicas）多 25%
                   # 示例：若 replicas=4，最多可同时运行 4 + 4×25% = 5 个 Pod（先创建 1 个新 Pod 再删除旧 Pod）
    maxUnavailable: 25%  # 允许不可用的 Pod 最大比例（或绝对值）
                         # 含义：更新过程中，不可用的 Pod 数量最多不超过期望副本数的 25%
                         # 示例：若 replicas=4，最多允许 4×25% = 1 个 Pod 不可用（每次删除旧 Pod 不超过 1 个）
  type: RollingUpdate  # 指定更新策略类型为滚动更新（Kubernetes 的默认策略）

Clean up Policy 清理策略

spec:
  # 1. 进度超时时间：控制 Deployment 更新的最大容忍时间
  progressDeadlineSeconds: 600  # 单位：秒（600秒 = 10分钟）
                                # 含义：若 Deployment 更新（如滚动更新）超过 10 分钟仍未完成（未达到可用状态），
                                # Kubernetes 会将其标记为“更新失败”（Progressing 状态变为 False，Reason 为 ProgressDeadlineExceeded），
                                # 但不会自动终止更新，需手动处理（如回滚、调整参数后重试）。

  # 2. 副本数：定义期望运行的 Pod 数量
  replicas: 1  # 期望保持 1 个 Pod 副本运行
               # Deployment 会通过控制器逻辑自动维持这个数量（如 Pod 故障时重建）。

  # 3. 历史版本保留限制：控制旧 ReplicaSet 的保留数量
  revisionHistoryLimit: 10  # 默认为 10，表示最多保留 10 个旧版本的 ReplicaSet（每个 ReplicaSet 对应一次 Deployment 更新）
                            # 超过此数量后，最旧的 ReplicaSet 会被自动删除，释放资源。
                            # 作用：旧 ReplicaSet 用于回滚操作（`kubectl rollout undo`），保留适量历史版本可兼顾回滚需求和资源消耗。

核心作用总结

  • progressDeadlineSeconds：防止更新过程无限期阻塞，为更新设置 “超时门槛”，便于及时发现更新异常（如镜像拉取失败、探针检测不通过导致的更新卡壳）。
  • replicas：定义应用的实例数量，是 Deployment 实现 “自愈” 和 “扩缩容” 的基础（结合 kubectl scale 可手动调整，结合 HPA 可自动调整）。
  • revisionHistoryLimit：平衡历史版本管理和资源占用，避免旧 ReplicaSet 过多导致集群资源浪费（尤其频繁更新的 Deployment）。

StatefulSet

是用于管理有状态的应用工作负载 API 对象。

Example: 

# API 版本，StatefulSet 在 apps/v1 版本中定义
apiVersion: apps/v1
# 资源类型为 StatefulSet（有状态集合，用于管理有状态应用）
kind: StatefulSet
metadata:
  # StatefulSet 的名称，用于标识该资源
  name: web
spec:
  # 选择器：用于匹配要管理的 Pod 标签，必须与下面 template.metadata.labels 一致
  selector:
    matchLabels:
      app: nginx # 匹配标签为 app: nginx 的 Pod
  # 服务名称：为 StatefulSet 中的 Pod 提供稳定网络标识的 Headless Service 名称
  # 需提前创建名为 nginx 的 Headless Service（无 ClusterIP）
  serviceName: "nginx"
  # 副本数：指定要运行的 Pod 数量，这里为 3 个
  replicas: 3 # 默认值为 1
  # 最小就绪秒数：Pod 就绪后等待多久才视为可用，避免频繁切换状态
  minReadySeconds: 10 # 默认值为 0
  # Pod 模板：定义 StatefulSet 生成的 Pod 的规格
  template:
    metadata:
      # Pod 的标签，必须与 spec.selector.matchLabels 匹配
      labels:
        app: nginx
    spec:
      # 终止宽限期：删除 Pod 时等待的秒数，确保优雅关闭
      terminationGracePeriodSeconds: 10
      # 容器配置列表
      containers:
      - name: nginx # 容器名称
        image: nginx:latest # 使用的镜像（最新版 Nginx）
        # 容器暴露的端口配置
        ports:
        - containerPort: 80 # 容器内监听的端口
          name: web # 端口名称，用于标识
        # 卷挂载：将存储卷挂载到容器内的指定路径
        volumeMounts:
        - name: www # 要挂载的卷名称（需与下面 volumes.name 对应）
          mountPath: /usr/share/nginx/html/index.html # 容器内的挂载路径（Nginx 默认首页位置）
      # 存储卷定义：供容器挂载的卷
      volumes:
      - name: www # 卷名称，与 volumeMounts.name 对应
        # 使用 hostPath 卷：将节点（宿主机）的路径挂载到容器
        hostPath:
          # 宿主机上的路径（这里指向宿主机的 /opt/index.html 文件）
          path: /opt/index.html
          # 路径类型：如果宿主机上不存在该文件，则自动创建一个空文件
          type: FileOrCreate
          # 其他可选类型说明：
          # - DirectoryOrCreate：路径不存在则创建目录
          # - Directory：必须存在目录，否则挂载失败
          # - File：必须存在文件，否则挂载失败
          # - Socket：必须存在 socket 文件
          # - CharDevice：必须存在字符设备
          # - BlockDevice：必须存在块设备
