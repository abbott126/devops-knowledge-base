SQL 语言

SQL（Structured Query Language，结构化查询语言）是用于管理关系型数据库（如 MySQL、Oracle、PostgreSQL）的标准编程语言，核心功能包括数据查询、插入、更新、删除，以及数据库结构的创建、修改和权限控制。它是关系型数据库的 “通用接口”，无论是开发、运维还是数据分析，都需掌握其基础语法与逻辑。

一、SQL 的核心定位与特点

  1. 非过程化语言
    只需描述 “要做什么”（如 “查询用户表中年龄大于 30 的数据”），无需指定 “怎么做”（如数据遍历顺序、底层存储读取逻辑），底层执行计划由数据库管理系统（DBMS）自动优化。
  2. 通用性强
    几乎所有关系型数据库（MySQL、Oracle、SQL Server、PostgreSQL 等）都支持 SQL，语法规则高度统一（核心语法无差异），仅在高级功能（如存储过程、函数）上存在少量 “方言”（如 MySQL 的LIMIT、Oracle 的ROWNUM）。
  3. 功能全面
    覆盖数据库全生命周期操作：从数据读写（DQL/DML）、结构定义（DDL），到事务控制（TCL）、权限管理（DCL），一站式满足关系型数据库的管理需求。
  4. 面向集合操作
    SQL 的操作对象和结果都是 “数据集合”（如一张表、一个查询结果集），而非单条数据，例如UPDATE users SET age=age+1 WHERE city='Beijing'可一次性更新符合条件的所有记录。

二、SQL 的四大核心分类

根据功能不同，SQL 可分为四大类，每类对应特定的数据库操作场景：

分类简称 全称 核心作用 常用命令示例
DQL Data Query Language 数据查询（从数据库中获取数据） SELECT
DML Data Manipulation Language 数据操纵（插入、更新、删除数据） INSERT、UPDATE、DELETE
DDL Data Definition Language 数据定义（创建 / 修改 / 删除数据库对象） CREATE、ALTER、DROP
DCL Data Control Language 数据控制（权限管理、事务控制） GRANT、REVOKE、COMMIT

此外，还有TCL（Transaction Control Language，事务控制语言） ，常被归为 DCL 的子集，核心命令为COMMIT（提交事务）、ROLLBACK（回滚事务）、SAVEPOINT（设置事务保存点）。

关键差异说明

  1. 精度限制：
  2. FLOAT 在存储超过 7 位有效数字时会四舍五入（如第 3 行的 0.000123456789 被近似为 0.000123457）
  3. DOUBLE 能更精确地保留更多位数（如同样的值保留到 0.000123456789）
  4. 自定义精度：
  5. 格式 FLOAT(M, D) 或 DOUBLE(M, D) 中，M 是总位数，D 是小数位数
  6. 例如 FLOAT(10, 4) 表示最多 10 位数字，其中 4 位是小数（如 12345.6789）

适用场景

  • 使用 FLOAT：对精度要求不高的场景（如温度、湿度等物理量），节省存储空间
  • 使用 DOUBLE：需要高精度的场景（如金融计算、科学实验数据）

Redis⽀持五种数据类型：String（字符串），Hash（哈希），List（列表），Set（集合）及Zset(sorted set：有序集合)。

字符串类型是redis最基础的数据结构，⾸先键是字符串类型，⽽且其他⼏种结构都是在字符串类型基础上构建

的，所以字符串类型为其他四种数据结构尊定了基础。

字符串类型实际上可以是简单的字符串、复杂的字符串（xml、json）、数字（整数、浮点数）、⼆进制（图⽚、

⾳频、视频）。

1.3、字符串应⽤场景

共享session：

⽤户登录后，⽤户刷新⼀次可能会重复登录，这个时候我们就将⽤户session集中管理，在这种模式下每次获取和

更新⽤户信息都可以从redis中获取。

限速：

当我们在登录时，⽤来限制为我⼿机接到验证码的时间，防⽌我们的短信接⼝不被频繁访问，会限制⽤户每分钟获

取验证码的频率。

数据持久化

https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

Redis 如何将数据写入磁盘持久性是指将数据写入持久存储，例如固态磁盘 （SSD）。Redis 提供了一系列持久化选项。这些包括：

  • RDB (Redis Database): RDB persistence performs point-in-time snapshots of your dataset at specified intervals.
**RDB**（Redis 数据库）：RDB 持久化按指定的时间间隔对数据集执行时间点快照。
  • AOF (Append Only File): AOF persistence logs every write operation received by the server. These operations can then be replayed again at server startup, reconstructing the original dataset. Commands are logged using the same format as the Redis protocol itself.
**AOF**（仅追加文件）：AOF 持久性记录服务器收到的每个写入作。然后可以在服务器启动时再次重放这些作，从而重建原始数据集。使用与 Redis 协议本身相同的格式记录命令。
  • No persistence: You can disable persistence completely. This is sometimes used when caching.
**无持久性** ：您可以完全禁用持久性。有时在缓存时使用这。
  • RDB + AOF: You can also combine both AOF and RDB in the same instance.
**RDB + AOF**：您还可以在同一实例中组合 AOF 和 RDB。

哨兵模式

哨兵是一个分布式系统，你可以在一个架构中运行多个哨兵进程，这些进程使用流言协议来接收关于Master主服务器是否下线的信息，并使用投票协议来决定是否执行自动故障迁移，以及选择哪个Slave作为新的Master。

一、哨兵模式概述

1.1、为什么要启动哨兵模式

当我们的主服务器宕机后，要手动的去切换主从模式，这样的人工干预，费事费力，还会造成一段时间我们的服务不能使用。所有我们要使用哨兵模式来解决这一问题。

1.2、什么是哨兵模式

哨兵是对Redis的系统的运行情况的监控，它是一个独立进程，功能有二个：

监控主机Redis和从机Redis是否运行正常；

主机Redis出现故障后自动将从机转化为主机

cluster 集群

Redis Cluster 是 Redis 官方提供的分布式数据库方案，它通过分片（Sharding） 来进行数据分布式存储，并提供复制（Replication） 和故障转移（Failover） 的高可用性功能。

它与之前的主从复制+Sentinel模式有根本性的不同。

核心特性与概念

1. 数据分片 (Sharding)
  • 核心思想： Redis Cluster 将整个数据集自动分割到 16384 个槽（slot）中。
  • 如何工作： 集群中的每个主节点（Master）负责处理一部分哈希槽。例如，一个三主节点的集群：
  • Node A 负责槽 0 - 5460
  • Node B 负责槽 5461 - 10922
  • Node C 负责槽 10923 - 16383
  • 数据定位： 当客户端要存取一个键时，会使用 CRC16 算法计算键的哈希值，然后对 16384 取模，得到该键对应的槽号，从而知道该由哪个节点处理。
  • 公式：slot = CRC16(key) % 16384
2. 高可用性 (High Availability)
  • 每个分片（即每个主节点）都可以拥有一个或多个从节点（Slave）。
  • 当某个主节点发生故障时，它的某个从节点会被自动提升为新的主节点，继续处理请求，整个过程对客户端透明。
  • 这与 Sentinel 的功能类似，但故障发现和转移是由 Cluster 自身节点通过 Gossip 协议 完成的，无需额外的 Sentinel 系统。
3. 去中心化架构 (Decentralized)
  • Redis Cluster 采用无中心架构，每个节点都保存有整个集群的元数据（如槽的分配信息、节点状态等）。
  • 节点之间通过 Gossip 协议 相互通信，交换状态信息，使得每个节点都能拥有完整的集群视图。
  • 客户端可以连接集群中的任意节点。如果该节点没有客户端请求的数据，它会返回一个 重定向指令（MOVED），告诉客户端正确的节点地址。

:warning: GTID Replication with Global Transaction Identifiers

概念：

本节介绍使用 全局事务标识符 （GTID）。使用 GTID 时，每个事务都可以在原始服务器上提交并由任何副本应用时进行识别和跟踪;这意味着在启动新副本或故障转移到新源时，使用 GTID 时无需引用日志文件或这些文件中的位置，这大大简化了这些任务。由于基于 GTID 的复制完全基于事务，因此很容易确定源和副本是否一致;只要在源上提交的所有事务也在副本上提交，就可以保证两者之间的一致性。您可以将基于语句或基于行的复制与 GTID 一起使用（参见第 19.2.1 节 ，“复制格式”）; 但是，为了获得最佳效果，我们建议您使用基于行的 格式。

GTID 格式和存储

全局事务标识符 （GTID） 是创建的唯一标识符，并与在源服务器（源）上提交的每个事务相关联。此标识符不仅对其来源的服务器是唯一的，而且在给定复制拓扑中的所有服务器中都是唯一的。
  • GTID = source_id:transaction_id
  • server_uuid:事务ID
    • dd220f24-8870-11f0-ad2e-5254007080f4:1-5

临时开启GTID

SET @@GLOBAL.enforce_gtid_consistency = WARN;
SET @@GLOBAL.enforce_gtid_consistency = ON;
SET @@GLOBAL.gtid_mode = OFF_PERMISSIVE;
SET @@GLOBAL.gtid_mode = ON_PERMISSIVE;
SHOW STATUS LIKE 'ONGOING_ANONYMOUS_TRANSACTION_COUNT';
SET @@GLOBAL.GTID_MODE = ON;

-- OFF：新的和复制事务都使用anonymous。 
-- OFF_PERMISSIVE：新事务是匿名的，同时允许复制的事务是GTID或匿名事务 
-- ON_PERMISSIVE：新事务使用GTID，同时允许复制的事务是GTID或匿名事务
 --ON: 新的和复制事务都使用GTID

变量名 值 含义说明
binlog_gtid_simple_recovery ON 用于控制在基于 GTID（全局事务标识符）的二进制日志（binlog）恢复机制方面的行为。 当设置为 ON 时，MySQL 在启动或者进行 binlog 相关恢复操作时，会采用一种相对简单直接的方式来处理 GTID 的信息，确保已提交的事务能正确地基于 GTID 从 binlog 中被识别和应用，有助于提升恢复效率以及保证数据一致性。
enforce_gtid_consistency ON 此参数强制开启 GTID 一致性检查。 开启后，会对数据库操作中的事务进行严格限制，确保所有事务的执行都符合 GTID 的一致性规则，例如禁止创建没有 GTID 的事务、禁止在事务中混合使用基于 GTID 和非基于 GTID 的操作等，以此来保证整个数据库集群中基于 GTID 的复制等功能稳定、准确地运行，避免因操作不一致导致的数据同步问题。
gtid_executed （空值） 该变量用于记录已经在当前服务器上执行过的所有 GTID 集合。 它会随着事务的提交不断更新，包含了各个已完成事务对应的 GTID 信息，是数据库用于跟踪自身事务执行历史以及在进行复制、恢复等操作时判断哪些事务已经处理过的重要依据。不过此处显示为空值，可能是尚未有事务执行或者尚未被更新显示（具体取决于当前数据库的状态和查询时机）。
gtid_executed_compression_period 0 用于控制 gtid_executed 变量所记录的 GTID 信息的压缩周期（单位为事务数量）。 值为 0 表示不进行自动压缩，设置为一个正整数 N 时，意味着每执行 N 个事务后，MySQL 会对 gtid_executed 中记录的 GTID 信息进行压缩整理，减少其占用的存储空间，优化内存和磁盘使用效率，但压缩操作也会带来一定的性能开销，所以通常根据实际情况来合理设置该值。
gtid_mode ON_PERMISSIVE 用于设定 GTID 的模式，有几种可选值： OFF 表示完全禁用 GTID 功能；ON_PERMISSIVE（当前值）表示允许在数据库中混合使用有 GTID 和无 GTID 的事务，对于不符合 GTID 规则的事务不会报错，只是记录警告信息，常用于从非 GTID 模式向 GTID 模式过渡的场景；ON 则强制要求所有事务都必须使用 GTID，严格遵循 GTID 相关规则，确保数据库操作的一致性；ON_FORCE 类似 ON，但在遇到不符合 GTID 规则的事务时会直接报错并拒绝执行。
gtid_next AUTOMATIC 决定下一个事务使用的 GTID 值如何生成。 AUTOMATIC 表示由 MySQL 自动根据内部机制分配下一个事务的 GTID，是一种常见且自动化程度高的方式，数据库会依据自身的事务执行顺序、复制配置等情况合理生成相应的 GTID，无需用户手动干预，方便且能保证 GTID 体系下事务的有序性和唯一性。
gtid_owned （空值） 用于标识当前服务器所 “拥有” 的 GTID 范围，也就是当前正在执行或者已经分配但尚未完成的事务对应的 GTID 集合。 如果为空，说明当前可能没有正在进行的相关事务或者尚未对其进行更新显示（同样取决于具体的数据库状态和查询时机），在多服务器复制环境等场景下可用于监控和了解各服务器的事务执行情况。
gtid_purged （空值） 记录了已经从二进制日志（binlog）中被清除掉的 GTID 集合。 在进行 binlog 的清理、过期数据删除等操作后，相应的 GTID 会被标记为已清除并记录在此变量中，方便数据库清楚哪些 GTID 对应的事务数据已经不存在了，有助于后续基于 GTID 的复制、恢复等操作判断数据完整性和历史情况。此处为空值可能是尚未有相关的 binlog 清理操作或者尚未更新显示该变量。
session_track_gtids OFF 用于控制是否在会话层面跟踪 GTID 信息。 当设置为 ON 时，服务器会在会话中记录每个事务对应的 GTID 情况，便于在会话内进行相关的事务监控、分析等操作；设置为 OFF（当前值）则不进行这样的跟踪，减少额外的会话数据记录开销，通常根据具体的应用场景和对 GTID 监控需求来决定是否开启。

  1. source_uuid：
  2. 这一列存储的是产生该 GTID 事务的服务器实例的通用唯一识别码（UUID）。通过这个 UUID 可以识别出是哪个具体的 MySQL 实例发起了对应的事务，在有多个 MySQL 实例构成的复制拓扑等场景中，可以据此区分不同源端产生的事务。
  3. 例如，其值可能类似 3e11fa47-71ca-11e1-9e33-c80aa9429562 这样的字符串格式，每个实例的 UUID 都是唯一的。
  4. transaction_id：
  5. 代表事务在其对应源实例上的编号，也就是在该 source_uuid 所标识的实例范围内，每个事务都有一个唯一的顺序编号。
  6. 它通常是一个数值类型的数据，用来区分同一实例产生的不同事务，按照事务执行的先后顺序依次递增。
  7. interval_start 和 interval_end：
  8. 这两列常用来表示事务区间，对于一个连续执行的一组 GTID 事务，它们可能会以区间的形式来记录，以节省存储空间并更高效地管理已执行事务信息。
  9. interval_start 是区间起始的事务编号，interval_end 是区间结束的事务编号，比如 interval_start 为 10，interval_end 为 20，表示从事务编号 10 到 20 这一组事务（在同一个 source_uuid 下）都已经被执行了。

半同步复制

官网地址：https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html

默认情况下，MySQL 复制是异步的。源将事件写入其二进制日志，副本在准备就绪时请求它们。源不知道副本是否或何时检索并处理了事务，并且不能保证任何事件都会到达任何副本。使用异步复制时，如果源崩溃，则它已提交的事务可能不会传输到任何副本。在这种情况下，从源到副本的故障转移可能会导致故障转移到缺少相对于源的事务的服务器。

半同步复制介于异步复制和完全同步复制之间。源等待至少一个副本接收并记录事件（所需的副本数是可配置的），然后提交事务。源不会等待所有副本确认接收，它只需要副本的确认，而不是事件已在副本端完全执行和提交。因此，半同步复制保证，如果源崩溃，它已提交的所有事务都已传输到至少一个副本.

与异步复制相比，半同步复制提供了改进的数据完整性，因为当提交成功返回时，已知数据至少存在于两个位置。在半同步源收到来自所需数量的副本的确认之前，事务处于保留状态且未提交。

rpl_semi_sync_source_wait_no_replica # 是 MySQL 半同步半同步复制（Semi-Sync Replication）** 中的一个系统变量，用于控制主库（Source）在没有从库（Replica）连接时的等待行为

AFTER_SYNC（默认）：源将每个事务写入其二进制日志和副本，并将二进制日志同步到磁盘。同步后，源等待交易数据的副本确认。收到确认后，源将事务提交给存储引擎，并将结果返回给客户端，然后客户端可以继续。

事务：

MySQL 事务（Transaction）是一组不可分割的数据库操作序列，这些操作要么全部成功执行，要么全部失败回滚，旨在保证数据库操作的原子性、一致性、隔离性和持久性（即 ACID 特性）。

一、事务的 ACID 特性

  1. 原子性（Atomicity）
    事务中的所有操作要么全部完成，要么全部不执行。例如，转账操作中 “扣减 A 账户金额” 和 “增加 B 账户金额” 必须同时成功或同时失败，避免出现数据不一致。
  2. 一致性（Consistency）
    事务执行前后，数据库从一个合法状态转换到另一个合法状态，满足预设的业务规则。例如，转账后 A 和 B 的总金额应与转账前相等。
  3. 隔离性（Isolation）
    多个事务并发执行时，彼此的操作互不干扰，每个事务都感觉不到其他事务的存在。MySQL 通过隔离级别控制并发事务的相互影响（见下文）。
  4. 持久性（Durability）
    事务一旦提交，其修改会永久保存到数据库中（即使系统崩溃也不会丢失）。MySQL 通过 redo 日志和刷盘机制实现持久性。

二、事务的基本操作

1. 开启事务

START TRANSACTION;  -- 或 BEGIN;

2. 执行操作

执行一系列 SQL 语句（如 INSERT、UPDATE、DELETE 等）：

UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- A账户扣减100
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- B账户增加100

3. 提交事务

所有操作成功后，提交事务（永久生效）：

COMMIT;

4. 回滚事务

若执行中出现错误，回滚事务（撤销所有操作）：

ROLLBACK;

5. 保存点（Savepoint）

在事务中设置保存点，可回滚到指定位置（而非整个事务）：

SAVEPOINT sp1;  -- 设置保存点sp1
-- 执行部分操作...
ROLLBACK TO sp1;  -- 回滚到sp1，保存点之后的操作被撤销

三、事务的隔离级别

当多个事务并发操作同一批数据时，可能出现脏读、不可重复读、幻读等问题。MySQL 提供了 4 种隔离级别（由低到高）：

隔离级别 含义 解决的问题
读未提交（Read Uncommitted） 一个事务可读取另一个未提交的事务数据。 无（性能最高，一致性最差）
读已提交（Read Committed） 一个事务只能读取另一个已提交的事务数据，避免脏读。 脏读
可重复读（Repeatable Read） 事务中多次读取同一数据的结果一致，避免不可重复读（MySQL 默认级别）。 脏读、不可重复读
串行化（Serializable） 事务串行执行（不并发），避免所有并发问题。 脏读、不可重复读、幻读
隔离级别相关操作
  • 查看当前隔离级别：
SELECT @@transaction_isolation;  -- MySQL 8.0+
-- 或 SELECT @@tx_isolation; （MySQL 5.x）
  • 设置隔离级别（全局或会话级别）
-- 全局生效（需重启会话）
SET GLOBAL transaction_isolation = 'READ COMMITTED';

-- 仅当前会话生效
SET SESSION transaction_isolation = 'REPEATABLE READ';

四、并发问题示例

  1. 脏读：事务 A 读取了事务 B 未提交的修改，若 B 回滚，A 读取的数据是 “无效的”。
  2. 不可重复读：事务 A 两次读取同一行数据，期间事务 B 修改并提交了该数据，导致 A 两次读取结果不一致。
  3. 幻读：事务 A 按条件查询数据，期间事务 B 插入了符合条件的新数据，A 再次查询时多了 “幻影” 行。

五、事务的使用场景

  • 金融交易（转账、支付）
  • 订单处理（创建订单 + 扣减库存）
  • 用户注册（插入用户 + 初始化关联数据）

六、注意事项

  1. 自动提交机制：MySQL 默认开启 autocommit=ON，每条 SQL 自动作为一个事务提交。开启显式事务后，需手动 COMMIT 或 ROLLBACK。
    可通过 SET autocommit = OFF; 关闭自动提交。
  2. 存储引擎支持：只有 InnoDB 引擎支持事务，MyISAM 等引擎不支持。
  3. 锁与性能：隔离级别越高，一致性越好，但并发性能越低（如串行化可能导致大量锁等待），需根据业务平衡选择。
  4. 长事务风险：长时间未提交的事务会占用锁资源，导致其他事务阻塞，建议事务尽可能短。

通过合理使用事务，可确保数据库操作的安全性和一致性，是处理关键业务数据的核心机制。

Example：

假设银行数据库中有一个 accounts 表，存储用户账户信息。现在需要实现：用户 A（id=1）向用户 B（id=2）转账 100 元。
这个过程需要两个关键操作：

  1. 从 A 的账户余额中扣减 100 元；
  2. 向 B 的账户余额中增加 100 元。
    这两个操作必须在同一个事务中执行，确保原子性。

步骤 1：创建测试表并插入数据

首先创建 accounts 表并初始化测试数据：

-- 创建账户表
CREATE TABLE accounts (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL,
  balance DECIMAL(10, 2) NOT NULL DEFAULT 0.00  -- 账户余额
) ENGINE=InnoDB;  -- 必须使用 InnoDB 引擎（支持事务）

-- 插入测试数据：A有200元，B有300元
INSERT INTO accounts (name, balance) VALUES 
('用户A', 200.00),
('用户B', 300.00);

执行一个完整的事务，确保扣款和收款都成功：

START TRANSACTION;

-- 1. 从用户A的账户扣减100元
UPDATE accounts 
SET balance = balance - 100 
WHERE id = 1;

-- 2. 向用户B的账户增加100元

COMMIT;

-- 先重置数据（确保A有100元，B有400元）

UPDATE accounts SET balance = 400 WHERE id = 2;

-- 开启事务
START TRANSACTION;

-- 1. 尝试从用户A的账户扣减200元（此时A只有100元，操作会执行但余额会变为负数）

SET balance = balance - 200 
WHERE id = 1;

-- 2. 假设此时发现A余额不足（实际业务中可通过程序判断余额是否为负）
-- 执行回滚，撤销所有操作

使用保存点（部分回滚案例）

-- 开启事务
START TRANSACTION;

-- 1. 从A扣减50元
UPDATE accounts SET balance = balance - 50 WHERE id = 1;

-- 2. 向B增加50元（假设这一步操作有误）

-- 重新执行正确的步骤2：向B增加50元

-- 提交事务
COMMIT;

-- 最终结果：A扣减50元，B增加50元，事务成功
SELECT * FROM accounts;

文档地址：

ONLINE: 后端服务器全面运行
SHUNNED:  后端服务器暂时停止使用，因为时间太短，连接错误过多，或者复制延迟超过允许的阈值

OFFLINE_SOFT:
    当服务器进入 OFFLINE_SOFT 模式时，不会向该服务器创建新连接，而现有连接将保留，直到它们返回到连接池或被销毁。换句话说，连接将保持使用状态，直到再次启用多路复用，例如当事务完成时。只要多路复用有效，就可以优雅地分离后端

OFFLINE_HARD
当服务器进入 OFFLINE_HARD 模式时，不会向该服务器创建新连接，并且会立即丢弃现有的空闲连接，而当前与客户端会话关联的后端连接会在客户端尝试使用它们时立即被丢弃。这相当于从主机组中删除服务器。在内部，将服务器设置为 OFFLINE_HARD 状态相当于删除服务器
