主从复制（AB）

复制使来自一个 MySQL 数据库服务器（称为源）的数据能够复制到一个或多个 MySQL 数据库服务器（称为副本）。默认情况下，复制是异步的;副本不需要永久连接即可从源接收更新。根据配置，您可以复制数据库中的所有数据库、选定的数据库，甚至数据库中的选定表。

复制的技术：

基于二进制日志的技术实现；

基于GTID技术实现复制；

[root@mysql-master ~]# tar xf  mysql-8.0.43-linux-glibc2.17-x86_64.tar.xz   -C /usr/local/mysql8/

[root@mysql-master mysql8]# ln  -s  mysql-8.0.43-linux-glibc2.17-x86_64 mysql

半同步复制

官网地址：https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html

默认情况下，MySQL 复制是异步的。源将事件写入其二进制日志，副本在准备就绪时请求它们。源不知道副本是否或何时检索并处理了事务，并且不能保证任何事件都会到达任何副本。使用异步复制时，如果源崩溃，则它已提交的事务可能不会传输到任何副本。在这种情况下，从源到副本的故障转移可能会导致故障转移到缺少相对于源的事务的服务器。

半同步复制介于异步复制和完全同步复制之间。源等待至少一个副本接收并记录事件（所需的副本数是可配置的），然后提交事务。源不会等待所有副本确认接收，它只需要副本的确认，而不是事件已在副本端完全执行和提交。因此，半同步复制保证，如果源崩溃，它已提交的所有事务都已传输到至少一个副本.

与异步复制相比，半同步复制提供了改进的数据完整性，因为当提交成功返回时，已知数据至少存在于两个位置。在半同步源收到来自所需数量的副本的确认之前，事务处于保留状态且未提交。

rpl_semi_sync_replica_trace_level # 主要用于控制从服务器（在半同步复制环境下常称为 “副本”，即replica）在参与半同步复制过程中的追踪（trace）详细程度，也就是日志记录的详细等级（level）。
rpl_semi_sync_source_enabled  # 控制是否在源服务器上启用半同步复制。要启用或禁用插件，请将此变量分别设置为1或0。默认值为0（关闭）。
rpl_semi_sync_replica_enabled # 控制是否在副本上启用半同步复制。
rpl_semi_sync_source_timeout  # 以毫秒为单位的值，用于控制源在超时并恢复到异步复制之前等待副本确认的提交时间。默认值为10000（10秒）。
rpl_semi_sync_source_wait_for_replica_count # 控制源在返回会话之前每个事务必须接收的副本确认数量。默认值为1，这意味着源只等待一个副本来确认收到事务事件。
rpl_semi_sync_source_wait_point  # 系统变量控制半同步源服务器在向提交事务的客户端返回状态之前等待事务接收的副本确认的点。这些值是允许的：
rpl_semi_sync_source_wait_no_replica # 是 MySQL 半同步半同步复制（Semi-Sync Replication）** 中的一个系统变量，用于控制主库（Source）在没有从库（Replica）连接时的等待行为

ON（默认值） 即使没有从库连接，主库仍会等待半同步复制的确认超时（由 rpl_semi_sync_source_timeout 控制，默认 10000 毫秒，即 10 秒）。超时后，主库会降级为异步复制，直接向客户端返回成功。
OFF 若没有从库连接，主库会立即跳过等待，直接以异步复制模式处理写操作（不等待超时），向客户端返回成功。

AFTER_SYNC（默认）：源将每个事务写入其二进制日志和副本，并将二进制日志同步到磁盘。同步后，源等待交易数据的副本确认。收到确认后，源将事务提交给存储引擎，并将结果返回给客户端，然后客户端可以继续。

AFTER_COMMIT：源将每个事务写入其二进制日志和副本，同步二进制日志，并将事务提交到存储引擎。提交后，源等待交易数据的副本确认。收到确认后，源将结果返回给客户端，然后客户端可以继续

解释含义：

Rpl_semi_sync_source_clients
含义：表示当前连接到主服务器（在半同步复制场景下常称为 “源”，即 source）且参与半同步复制的从服务器（副本）的数量。
示例中的值及说明：此处值为 1，意味着有 1 个从服务器正在与该主服务器以半同步复制的方式进行连接并同步数据，反映了当前参与半同步复制的从节点个数情况。


Rpl_semi_sync_source_net_avg_wait_time
含义：记录的是主服务器等待从服务器通过网络确认已接收并处理事务的平均等待时间（以毫秒为单位）。这个时间统计是针对网络传输确认环节的平均耗时情况。
示例中的值及说明：值为 0 说明在当前统计阶段内，主服务器等待从服务器网络确认的平均耗时几乎可以忽略不计，可能是还没有足够多的事务操作发生来产生有意义的平均等待时间积累，或者从服务器响应非常及时，使得平均等待时间为零。

Rpl_semi_sync_source_net_wait_time
含义：表示主服务器等待从服务器通过网络确认已接收并处理事务的总等待时间（以毫秒为单位）。与平均等待时间不同，它是整体累计的等待时长。
示例中的值及说明：值为 0 表明截至目前，主服务器在等待从服务器网络确认事务接收与处理这件事上，总的等待时长累计为零，同样可能是由于业务操作还较少等原因导致。

Rpl_semi_sync_source_net_waits
含义：统计主服务器等待从服务器通过网络确认已接收并处理事务的次数。
示例中的值及说明：值为 0 意味着到目前为止，主服务器还未曾经历需要等待从服务器网络确认的情况，或者说相关等待情况还未发生过足够多的次数以体现出一个有别于零的统计值。

Rpl_semi_sync_source_no_times
含义：记录的是由于各种原因（比如从服务器没有及时响应等），主服务器无法进入半同步复制模式而不得不退回到异步复制模式的次数。
示例中的值及说明：值为 0 表示截至当前，主服务器在进行复制操作时，尚未出现过因异常情况而被迫从半同步复制切换回异步复制的情形，体现了半同步复制过程的稳定性情况，没有发生这种降级切换的情况。

Rpl_semi_sync_source_no_tx
含义：表示在主服务器上，那些没有能够进入半同步复制状态的事务数量。也就是因为各种条件限制没能按照半同步复制要求完成相应流程的事务个数统计。
示例中的值及说明：值为 0 说明目前主服务器执行的所有事务都顺利进入了半同步复制流程，不存在事务被排除在半同步复制之外的情况，侧面反映了半同步复制机制在事务处理方面目前运行良好。

Rpl_semi_sync_source_status
含义：显示主服务器当前半同步复制的状态，ON 表示半同步复制处于开启状态，OFF 则表示处于关闭状态。
示例中的值及说明：此处状态为 ON，表明当前主服务器的半同步复制功能是正常开启的，正在按照半同步复制的规则和机制来处理事务并与从服务器进行数据同步操作。

Rpl_semi_sync_source_timefunc_failures
含义：统计在半同步复制过程中，与时间相关的函数出现故障的次数。这些时间相关函数通常用于计时、判断超时等操作，若出现故障可能影响半同步复制中对时间相关流程的准确把控。
示例中的值及说明：值为 0 表示在当前半同步复制的运行过程中，时间相关的函数都正常工作，没有出现过故障情况，意味着半同步复制在时间把控方面的基础机制是可靠的。

Rpl_semi_sync_source_tx_avg_wait_time
含义：主服务器等待从服务器确认事务（从发起事务到收到从服务器确认整个过程）的平均等待时间（以毫秒为单位）。它综合考量了整个事务在半同步复制流程中的等待情况来计算平均耗时。
示例中的值及说明：值为 0 说明当前平均来看，主服务器在事务等待从服务器确认的这个环节，几乎没有花费额外的时间，整体的等待情况处于理想状态，不过也可能是还没有足够多有代表性的事务发生来产生有意义的平均耗时统计。

Rpl_semi_sync_source_tx_wait_time
含义：主服务器等待从服务器确认事务（从发起事务到收到从服务器确认整个过程）的总等待时间（以毫秒为单位）。它是对所有事务等待时间的累计统计值。
示例中的值及说明：值为 0 表明截至目前，主服务器在等待从服务器确认事务这件事上，总的累计等待时长是零，和前面一些平均等待时间等指标为零的情况类似，可能是业务操作还未频繁到足以产生等待时长积累的程度。

Rpl_semi_sync_source_tx_waits
含义：统计主服务器等待从服务器确认事务的次数。也就是主服务器发起事务后，等待从服务器反馈确认信息的次数累计情况。
示例中的值及说明：值为 0 意味着到现在为止，主服务器还没有经历过等待从服务器确认事务的情况，或者说相关情况发生次数过少尚未体现出有别于零的统计值。

Rpl_semi_sync_source_wait_pos_backtraverse
含义：这个变量涉及到半同步复制中主服务器等待从服务器确认时，在二进制日志位置回溯等相关操作的统计情况，具体来说，统计的是等待过程中需要回溯二进制日志位置的次数。通常用于更深入分析半同步复制过程中二进制日志相关的复杂操作情况。
示例中的值及说明：值为 0 表示在当前半同步复制运行阶段，还没有出现过需要在等待从服务器确认时回溯二进制日志位置的情况，反映了半同步复制在二进制日志处理方面目前较为顺畅。

Rpl_semi_sync_source_wait_sessions
含义：统计主服务器等待从服务器确认事务时涉及到的会话数量情况，也就是有多少个会话在等待从服务器反馈确认信息，用于从会话角度来衡量半同步复制中的等待情况。
示例中的值及说明：值为 0 说明截至目前，还不存在会话在等待从服务器确认事务的这种情况，体现了当前半同步复制在会话层面上的等待情况处于理想状态。

Rpl_semi_sync_source_yes_tx
含义：表示在主服务器上成功以半同步复制方式完成的事务数量。它统计的是按照半同步复制流程正常推进并最终成功的事务个数。
示例中的值及说明：值为 0 虽然说明目前成功通过半同步复制完成的事务数量还不多，但结合前面其他变量的值来看，目前整个半同步复制机制处于正常开启且尚未有过多业务操作产生有意义统计值的一种初始运行状态。

事务：

MySQL 事务（Transaction）是一组不可分割的数据库操作序列，这些操作要么全部成功执行，要么全部失败回滚，旨在保证数据库操作的原子性、一致性、隔离性和持久性（即 ACID 特性）。

一、事务的 ACID 特性

  1. 原子性（Atomicity）
    事务中的所有操作要么全部完成，要么全部不执行。例如，转账操作中 “扣减 A 账户金额” 和 “增加 B 账户金额” 必须同时成功或同时失败，避免出现数据不一致。
  2. 一致性（Consistency）
    事务执行前后，数据库从一个合法状态转换到另一个合法状态，满足预设的业务规则。例如，转账后 A 和 B 的总金额应与转账前相等。
  3. 隔离性（Isolation）
    多个事务并发执行时，彼此的操作互不干扰，每个事务都感觉不到其他事务的存在。MySQL 通过隔离级别控制并发事务的相互影响（见下文）。
  4. 持久性（Durability）
    事务一旦提交，其修改会永久保存到数据库中（即使系统崩溃也不会丢失）。MySQL 通过 redo 日志和刷盘机制实现持久性。

二、事务的基本操作

1. 开启事务

START TRANSACTION;  -- 或 BEGIN;

2. 执行操作

执行一系列 SQL 语句（如 INSERT、UPDATE、DELETE 等）：

UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- A账户扣减100
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- B账户增加100

3. 提交事务

所有操作成功后，提交事务（永久生效）：

COMMIT;

4. 回滚事务

若执行中出现错误，回滚事务（撤销所有操作）：

ROLLBACK;

5. 保存点（Savepoint）

在事务中设置保存点，可回滚到指定位置（而非整个事务）：

SAVEPOINT sp1;  -- 设置保存点sp1
-- 执行部分操作...
ROLLBACK TO sp1;  -- 回滚到sp1，保存点之后的操作被撤销

三、事务的隔离级别

当多个事务并发操作同一批数据时，可能出现脏读、不可重复读、幻读等问题。MySQL 提供了 4 种隔离级别（由低到高）：

隔离级别 含义 解决的问题
读未提交（Read Uncommitted） 一个事务可读取另一个未提交的事务数据。 无（性能最高，一致性最差）
读已提交（Read Committed） 一个事务只能读取另一个已提交的事务数据，避免脏读。 脏读
可重复读（Repeatable Read） 事务中多次读取同一数据的结果一致，避免不可重复读（MySQL 默认级别）。 脏读、不可重复读
串行化（Serializable） 事务串行执行（不并发），避免所有并发问题。 脏读、不可重复读、幻读
隔离级别相关操作
  • 查看当前隔离级别：
SELECT @@transaction_isolation;  -- MySQL 8.0+
-- 或 SELECT @@tx_isolation; （MySQL 5.x）
  • 设置隔离级别（全局或会话级别）
-- 全局生效（需重启会话）
SET GLOBAL transaction_isolation = 'READ COMMITTED';

-- 仅当前会话生效
SET SESSION transaction_isolation = 'REPEATABLE READ';

四、并发问题示例

  1. 脏读：事务 A 读取了事务 B 未提交的修改，若 B 回滚，A 读取的数据是 “无效的”。
  2. 不可重复读：事务 A 两次读取同一行数据，期间事务 B 修改并提交了该数据，导致 A 两次读取结果不一致。
  3. 幻读：事务 A 按条件查询数据，期间事务 B 插入了符合条件的新数据，A 再次查询时多了 “幻影” 行。

五、事务的使用场景

  • 金融交易（转账、支付）
  • 订单处理（创建订单 + 扣减库存）
  • 用户注册（插入用户 + 初始化关联数据）

六、注意事项

  1. 自动提交机制：MySQL 默认开启 autocommit=ON，每条 SQL 自动作为一个事务提交。开启显式事务后，需手动 COMMIT 或 ROLLBACK。
    可通过 SET autocommit = OFF; 关闭自动提交。
  2. 存储引擎支持：只有 InnoDB 引擎支持事务，MyISAM 等引擎不支持。
  3. 锁与性能：隔离级别越高，一致性越好，但并发性能越低（如串行化可能导致大量锁等待），需根据业务平衡选择。
  4. 长事务风险：长时间未提交的事务会占用锁资源，导致其他事务阻塞，建议事务尽可能短。

通过合理使用事务，可确保数据库操作的安全性和一致性，是处理关键业务数据的核心机制。

Example：

假设银行数据库中有一个 accounts 表，存储用户账户信息。现在需要实现：用户 A（id=1）向用户 B（id=2）转账 100 元。
这个过程需要两个关键操作：

  1. 从 A 的账户余额中扣减 100 元；
  2. 向 B 的账户余额中增加 100 元。
    这两个操作必须在同一个事务中执行，确保原子性。

步骤 1：创建测试表并插入数据

首先创建 accounts 表并初始化测试数据：

-- 创建账户表
CREATE TABLE accounts (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL,
  balance DECIMAL(10, 2) NOT NULL DEFAULT 0.00  -- 账户余额
) ENGINE=InnoDB;  -- 必须使用 InnoDB 引擎（支持事务）

-- 插入测试数据：A有200元，B有300元
INSERT INTO accounts (name, balance) VALUES 
('用户A', 200.00),
('用户B', 300.00);

正常转账事务（成功案例）

执行一个完整的事务，确保扣款和收款都成功：

-- 开启事务
START TRANSACTION;

-- 1. 从用户A的账户扣减100元
UPDATE accounts 
SET balance = balance - 100 
WHERE id = 1;

-- 2. 向用户B的账户增加100元
UPDATE accounts 
SET balance = balance + 100 
WHERE id = 2;

-- 检查操作结果（可选，实际业务中可通过程序判断）
SELECT * FROM accounts;

-- 确认无误后提交事务（操作永久生效）
COMMIT;

转账失败事务（回滚案例）

-- 先重置数据（确保A有100元，B有400元）
UPDATE accounts SET balance = 100 WHERE id = 1;
UPDATE accounts SET balance = 400 WHERE id = 2;

-- 开启事务
START TRANSACTION;

-- 1. 尝试从用户A的账户扣减200元（此时A只有100元，操作会执行但余额会变为负数）
UPDATE accounts 
SET balance = balance - 200 
WHERE id = 1;

-- 2. 假设此时发现A余额不足（实际业务中可通过程序判断余额是否为负）
-- 执行回滚，撤销所有操作
ROLLBACK;

-- 检查结果：数据恢复到事务开始前的状态
SELECT * FROM accounts;

使用保存点（部分回滚案例）

-- 开启事务
START TRANSACTION;

-- 1. 从A扣减50元
UPDATE accounts SET balance = balance - 50 WHERE id = 1;

-- 设置保存点sp1
SAVEPOINT sp1;

-- 2. 向B增加50元（假设这一步操作有误）
UPDATE accounts SET balance = balance + 50 WHERE id = 3;  -- id=3不存在，操作无效果

-- 回滚到保存点sp1（仅撤销保存点后的操作，即步骤2的错误操作）
ROLLBACK TO sp1;

-- 重新执行正确的步骤2：向B增加50元
UPDATE accounts SET balance = balance + 50 WHERE id = 2;

-- 提交事务
COMMIT;

-- 最终结果：A扣减50元，B增加50元，事务成功
SELECT * FROM accounts;

mysql> INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
#在本地找不到library库文件
ERROR 1126 (HY000): Can't open shared library '/usr/local/mysql/lib/plugin/semisync_source.so' (errno: 11 /usr/local/mysql/lib/plugin/semisync_source.so: cannot open shared object file: No such file or directory)

plugin_dir =/usr/local/mysql8/mysql/lib/plugin
