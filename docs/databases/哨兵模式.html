哨兵模式

哨兵模式

哨兵是一个分布式系统，你可以在一个架构中运行多个哨兵进程，这些进程使用流言协议来接收关于Master主服务器是否下线的信息，并使用投票协议来决定是否执行自动故障迁移，以及选择哪个Slave作为新的Master。

一、哨兵模式概述

1.1、为什么要启动哨兵模式

当我们的主服务器宕机后，要手动的去切换主从模式，这样的人工干预，费事费力，还会造成一段时间我们的服务不能使用。所有我们要使用哨兵模式来解决这一问题。

1.2、什么是哨兵模式

哨兵是对Redis的系统的运行情况的监控，它是一个独立进程，功能有二个：

监控主机Redis和从机Redis是否运行正常；

主机Redis出现故障后自动将从机转化为主机

多个哨兵(自己实现）

cluster 集群

Redis Cluster 是 Redis 官方提供的分布式数据库方案，它通过分片（Sharding） 来进行数据分布式存储，并提供复制（Replication） 和故障转移（Failover） 的高可用性功能。

它与之前的主从复制+Sentinel模式有根本性的不同。

核心特性与概念

1. 数据分片 (Sharding)
  • 核心思想： Redis Cluster 将整个数据集自动分割到 16384 个槽（slot）中。
  • 如何工作： 集群中的每个主节点（Master）负责处理一部分哈希槽。例如，一个三主节点的集群：
  • Node A 负责槽 0 - 5460
  • Node B 负责槽 5461 - 10922
  • Node C 负责槽 10923 - 16383
  • 数据定位： 当客户端要存取一个键时，会使用 CRC16 算法计算键的哈希值，然后对 16384 取模，得到该键对应的槽号，从而知道该由哪个节点处理。
  • 公式：slot = CRC16(key) % 16384
2. 高可用性 (High Availability)
  • 每个分片（即每个主节点）都可以拥有一个或多个从节点（Slave）。
  • 当某个主节点发生故障时，它的某个从节点会被自动提升为新的主节点，继续处理请求，整个过程对客户端透明。
  • 这与 Sentinel 的功能类似，但故障发现和转移是由 Cluster 自身节点通过 Gossip 协议 完成的，无需额外的 Sentinel 系统。
3. 去中心化架构 (Decentralized)
  • Redis Cluster 采用无中心架构，每个节点都保存有整个集群的元数据（如槽的分配信息、节点状态等）。
  • 节点之间通过 Gossip 协议 相互通信，交换状态信息，使得每个节点都能拥有完整的集群视图。
  • 客户端可以连接集群中的任意节点。如果该节点没有客户端请求的数据，它会返回一个 重定向指令（MOVED），告诉客户端正确的节点地址。

二、 修改配置文件(所有节点上的配置文件都需要修改)

我们使用是多实例；需要修改端口；如何使用node节点，就不需要修改端口

我们使用是多实例；需要修改进程ID；如何使用node节点，就不需要修改进程ID

protected-mode no
port 6381 #每个节点上端口；
tcp-backlog 511
timeout 0
tcp-keepalive 300
daemonize yes
pidfile /var/run/redis_6381.pid  #修改pid
loglevel notice
logfile "/usr/local/redis/logs/redis6381.log"  #修改主机节点日志
dir /usr/local/redis/redis-6381/   #类似家目录
cluster-enabled yes #开启集群的模式
cluster-config-file nodes-6381.conf  #集群维护的配置文件
cluster-node-timeout 15000   #集群超时时间
