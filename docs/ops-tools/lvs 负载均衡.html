NFS 网络文件系统（共享存储组件）

NFS是基于UDP/IP协议的应用，其实现主要是采用远程过程调用RPC机制，RPC提供了一组与机器、操作系统以及底层传送协议无关的存取远程文件的操作。RPC采用了XDR的支持。XDR是一种与机器无关的数据描述编码的协议，他以独立与任意机器体系结构的格式对网上传送的数据进行编码和解码，支持在异构系统之间数据的传送.

部署

[root@nginx-proxy ~]# yum -y install nfs-utils  rpcbind
[root@nginx-proxy ~]# systemctl   enable  --now nfs  rpcbind

/         192.168.19.0(rw)
/phpmyadmin  192.168.18.0(rw)

重启

[root@nginx-proxy ~]# systemctl restart  rpcbind nfs

负载均衡及高可用

负载均衡

负载均衡（Load Balancing）是一种分布式系统核心技术，通过将客户端的请求（如 HTTP 请求、TCP 连接）均匀分发到多个后端服务器集群，实现 “避免单点过载、提升系统并发能力、增强服务可用性” 的目标。它是高可用（HA）、高并发架构的核心组件，广泛应用于网站、API 服务、数据库等场景。

一、核心定义与本质

负载均衡的本质是 “资源调度优化”：

  • 前端用户 / 客户端的请求不直接访问后端服务器，而是先发送到 “负载均衡器（Load Balancer）”；
  • 负载均衡器根据预设规则（如 “轮询”“最小连接数”）选择一台健康的后端服务器，将请求转发给它；
  • 后端服务器处理请求后，将响应通过负载均衡器返回给客户端（部分架构支持 “直接响应”，减少负载均衡器压力）。

简单来说：负载均衡器就像 “交通指挥员”，把大量车辆（请求）引导到不同车道（后端服务器），避免单车道拥堵，同时确保车道（服务器）正常通行。

二、负载均衡的核心作用

  1. 提高系统并发能力
    单台服务器的 CPU、内存、网络带宽有限，并发请求超过阈值会导致响应变慢甚至宕机。通过多台服务器分担请求，可线性提升系统的并发处理能力（如 10 台服务器理论可支撑 10 倍于单台的并发量）。
  2. 避免单点故障（提升可用性）
    若所有请求集中到一台服务器，该服务器故障会导致整个服务不可用（单点故障）。负载均衡器会通过 “健康检查” 实时监测后端服务器状态，自动剔除故障节点，将请求转发到正常节点，确保服务不中断（可用性通常可达 99.99% 以上）。
  3. 优化资源利用率
    避免部分服务器闲置、部分服务器过载的 “资源浪费 + 过载崩溃” 问题，让集群中所有服务器的负载（CPU 利用率、连接数、内存占用）趋于均衡。
  4. 增强系统扩展性
    当业务增长需要提升性能时，无需改造核心架构，只需向负载均衡集群中新增后端服务器，负载均衡器会自动将请求分发到新节点，实现 “水平扩展”。
  5. 附加功能支撑
    现代负载均衡器还支持SSL 卸载（集中处理 HTTPS 加密解密，减轻后端压力）、会话保持（确保同一用户的请求始终转发到同一服务器，避免登录状态丢失）、流量控制（限制恶意请求，防止 DDoS 攻击）等功能。

  • 健康检查：负载均衡器定期向后端服务器发送 “心跳包”（如 TCP 连接测试、HTTP 请求 /health），若某服务器连续失败，则标记为 “不可用”，不再分发请求。
  • 请求转发：根据预设算法选择后端服务器，转发请求并建立 “请求链路”。
  • 响应返回：后端服务器处理完成后，将响应通过负载均衡器返回给客户端（部分架构支持 “直接返回”，即后端服务器直接向客户端发送响应，减少负载均衡器瓶颈）。

常见负载均衡算法

算法决定了负载均衡器 “如何选择后端服务器”，需根据业务场景（如后端服务器配置是否一致、是否需要会话保持）选择，主要分为静态算法和动态算法两类：

算法类型 算法名称 原理 适用场景 优缺点
静态算法 轮询（Round Robin） 按顺序依次将请求分发到后端服务器（1→2→3→1→2→3...） 后端服务器配置完全一致（CPU、内存、带宽相同） 优点：简单高效；缺点：若服务器性能差异大，会导致负载不均
静态算法 加权轮询（Weighted RR） 给性能好的服务器分配更高 “权重”，权重越高接收请求越多（如权重 3:1，服务器 1 接收 3 次、服务器 2 接收 1 次） 后端服务器配置不一致（如部分服务器 CPU 更强） 优点：适配性能差异；缺点：无法动态调整权重（需手动配置）
静态算法 IP 哈希（IP Hash） 根据客户端 IP 地址计算哈希值，映射到固定后端服务器 需要 “会话保持” 的场景（如用户登录状态、购物车数据存储在服务器本地） 优点：无需额外存储会话；缺点：若某服务器故障，该 IP 段用户请求会失败
动态算法 最小连接数（Least Connections） 实时统计后端服务器的活跃连接数，将请求分发到连接数最少的服务器 请求处理时间差异大的场景（如部分请求耗时久、部分耗时短） 优点：动态适配负载；缺点：需实时统计连接数，略增加负载均衡器开销
动态算法 最快响应时间（Fastest Response Time） 选择 “平均响应时间最短” 的服务器，兼顾连接数和处理速度 对响应延迟敏感的场景（如金融交易、实时通信） 优点：优先保障低延迟；缺点：需统计响应时间，算法复杂度较高
动态算法 最少负载（Least Load） 综合 CPU 利用率、内存占用、磁盘 I/O 等指标，选择负载最低的服务器 后端服务器负载类型多样（如混合 CPU 密集型、I/O 密集型任务） 优点：最精准的负载均衡；缺点：需收集多维度指标，性能开销较大

负载均衡的部署架构（四层 vs 七层）

对比维度 四层负载均衡（L4） 七层负载均衡（L7）
工作层级 OSI 模型第 4 层（传输层），基于IP 地址 + 端口 OSI 模型第 7 层（应用层），基于应用层协议内容（如 HTTP 路径、域名、请求头）
分发依据 客户端 IP、目标 IP、端口（如 TCP 80/443） HTTP URL 路径（如/api→服务器 A，/static→服务器 B）、域名、Cookie、请求参数
核心功能 转发 TCP/UDP 连接，支持高并发、低延迟 路径路由、域名路由、SSL 卸载、会话保持、请求过滤（如拦截恶意请求）
性能 性能极高（仅处理传输层数据，无需解析应用内容），支持百万级并发 性能略低（需解析应用层协议），支持十万级并发
适用场景 TCP 协议服务（如数据库、Redis、WebSocket）、高并发 HTTP 服务 需按应用内容分发的场景（如微服务路由、静态 / 动态资源分离、多域名共享 IP）
典型工具 LVS（Linux Virtual Server）、F5 BIG-IP（硬件） Nginx、HAProxy、Apache Traffic Server

What is the Linux Virtual Server

The Linux Virtual Server is a highly scalable and highly available server built on a cluster of real servers, with the load balancer running on the Linux operating system. The architecture of the server cluster is fully transparent to end users, and the users interact as if it were a single high-performance virtual server. For more information, click here.

调度算法：
  • Round-Robin Scheduling 循环调度

循环调度算法将每个传入请求发送到其列表中的下一个服务器。

  • Weighted Round-Robin Scheduling 加权轮询调度

加权轮询调度旨在更好地处理不同处理能力的服务器。可以为每个服务器分配一个权重，一个表示处理能力的整数值。

  • Least-Connection Scheduling 最少连接调度

最少连接调度算法将网络连接定向到已建立连接数最少的服务器。这是动态调度算法之一;因为它需要动态计算每个服务器的实时连接。对于管理具有类似性能的服务器集合的虚拟服务器，当请求负载变化很大时，最少连接调度有助于平滑分配。虚拟服务器会将请求定向到活动连接最少的真实服务器。

  • Weighted Least-Connection Scheduling 加权最小连接调度

加权最小连接调度是最小连接调度的超集，您可以在其中为每个实际服务器分配性能权重。权重值较高的服务器将在任何时候接收更大比例的实时连接。虚拟服务器管理员可以为每个真实服务器分配一个权重，并将网络连接调度到每台服务器，其中每台服务器的当前实时连接数的百分比与其权重成比。默认权重为 1。

  • Locality-Based Least-Connection Scheduling 基于局部的最小连接调度

基于局部的最小连接调度算法用于目标 IP 负载均衡。它通常用于缓存集群。如果服务器处于活动状态且处于负载状态，则此算法通常会将发往 IP 地址的数据包定向到其服务器。如果服务器过载（其活动连接数大于其权重），并且有一台服务器处于一半负载状态，则将加权最小连接服务器分配给此 IP 地址。

  • Locality-Based Least-Connection with Replication Scheduling 基于局部的最小连接与复制调度

基于局部的最小连接与复制调度算法也用于目标 IP 负载均衡。它通常用于缓存集群。它与 LBLC 调度的不同之处在于：负载均衡器维护从目标到一组可以为目标提供服务的服务器节点的映射。对目标的请求被分配给目标服务器集中连接最少的节点。如果服务器集中的所有节点都过载，它会在集群中选取一个连接最少的节点，并将其添加到目标的服务器集中。如果服务器集在指定时间内未被修改，则从服务器集中删除负载最多的节点，以避免高度复制。

  • Destination Hashing Scheduling 目标哈希调度

目标哈希调度算法通过按目标 IP 地址查找静态分配的哈希表，将网络连接分配给服务器。

  • Source Hashing Scheduling 源哈希调度

源哈希调度算法通过按源 IP 地址查找静态分配的哈希表，将网络连接分配给服务器。

  • Shortest Expected Delay Scheduling 最短预期延迟调度

最短预期延迟调度算法将网络连接分配给具有最短预期延迟的服务器。如果发送到第 i 台服务器，作业将经历的预期延迟为 （Ci + 1） / Ui，其中 Ci 是第 i 台服务器上的连接数，Ui 是第 i 台服务器的固定服务速率（权重）。

  • Never Queue Scheduling 从不排队调度

从不排队调度算法采用双速模型。当有空闲服务器可用时，作业将被发送到空闲服务器，而不是等待快速服务器。当没有空闲服务器可用时，作业将被发送到最小化其预期延迟的服务器（最短预期延迟调度算法）。

-n --numeric numeric output of addresses and ports

-a --add-server. add real server with options

-r --real-server server-address server-address is host (and port)

模式

--gatewaying -g gatewaying (direct routing) (default)

--ipip -i ipip encapsulation (tunneling)

--masquerading -m masquerading (NAT)

--save -S save rules to stdout

  • ESTABLISHED：已建立的连接，客户端与后端服务器之间的通信正常进行。
  • SYN_RECV：LVS 已收到客户端的 SYN 报文（连接请求），并已转发给后端服务器，但尚未收到服务器的 SYN-ACK 响应。
  • FIN_WAIT：连接进入关闭阶段，一端已发送 FIN 报文（终止连接请求），等待另一端确认。
  • TIME_WAIT：连接已关闭，处于超时等待状态（防止延迟报文干扰新连接）。
  • NONE：极少数情况下，TCP 连接状态未被正确跟踪时显示（通常为异常状态）

高可用（HA）体系的实现依赖于 “硬件冗余” 和 “软件组件” 的协同配合，硬件是基础（避免物理单点故障），软件是核心（实现故障检测、自动切换、数据同步）。以下从 “硬件层” 和 “软件组件层” 详细拆解高可用体系的核心构成，以及各部分的作用和典型方案：

一、高可用核心硬件：冗余是核心原则

硬件层的目标是消除物理单点故障，通过 “多设备备份” 确保电源、网络、存储、服务器等关键物理组件故障时，系统仍能运行。常见高可用硬件及设计思路如下：

1. 服务器硬件：避免单服务器宕机
  • 核心需求：服务器是业务运行的载体，需通过 “多节点冗余” 确保单台服务器故障不影响服务。
  • 典型方案：
  • 主备服务器：1 台主服务器运行业务，1 台备服务器待机（如 LVS 主备、Nginx 主备），主节点故障后备节点接管；
  • 集群服务器：多台服务器同时运行业务（如 Web 集群、数据库集群），通过负载均衡分摊流量，单节点故障后其他节点自动承接；
  • 硬件规格冗余：单台服务器内部的 “冗余设计”（如双电源、双网卡），避免电源 / 网卡单点故障导致服务器离线。
  • 示例：电商平台部署 3 台 Web 服务器组成集群，即使 1 台宕机，剩余 2 台仍可支撑业务，用户无感知。
2. 网络硬件：避免网络链路中断
  • 核心需求：网络是客户端与服务的连接通道，需通过 “多链路、多设备” 确保网络不中断。
  • 典型方案：
  • 双网卡 / 多网卡：服务器配置 2 块及以上网卡，分别连接不同交换机，避免单网卡故障导致服务器断网；
  • 冗余交换机：核心交换机、接入交换机部署 “主备模式” 或 “堆叠模式”（如华为 IRF、Cisco VSS），单交换机故障后，另一台自动接管所有端口；
  • 多网络链路：机房接入多条不同运营商的宽带（如电信 + 联通），通过 BGP 路由或链路聚合（LACP）实现链路冗余，单链路中断后自动切换到备用链路；
  • 负载均衡器（硬件）：核心入口部署硬件负载均衡器（如 F5 BIG-IP、Citrix NetScaler），通常采用 “主备模式”，避免负载均衡器成为单点故障。
  • 示例：企业核心交换机部署 2 台堆叠，单台交换机断电后，所有接入设备的网络连接不中断，业务正常运行。
3. 存储硬件：避免数据存储故障
  • 核心需求：数据是业务的核心，需通过 “多副本存储” 确保硬盘、存储设备故障时数据不丢失、可访问。
  • 典型方案：
  • RAID 磁盘阵列：单台服务器或存储设备内，多块硬盘组成 RAID（如 RAID1、RAID5、RAID6），实现 “硬盘冗余”——RAID1（双盘互备）：1 块硬盘故障，另一块硬盘仍有完整数据；RAID5（至少 3 盘）：允许 1 块硬盘故障，通过校验数据恢复；
  • SAN/NAS 集群：企业级存储设备（如 EMC VMAX、华为 OceanStor）部署 “双控制器” 或 “多节点集群”，单控制器 / 节点故障后，其他节点接管存储服务，确保数据读写不中断；
  • 分布式存储：基于多台服务器的本地硬盘构建分布式存储集群（如 Ceph、GlusterFS），数据自动分成多副本（如 3 副本）存储在不同节点，单节点 / 硬盘故障不影响数据可用性。
  • 示例：数据库服务器采用 RAID5 阵列（3 块硬盘），若 1 块硬盘损坏，可通过剩余 2 块硬盘的校验数据恢复，数据库无需停机。
4. 电源与机房环境：避免基础设施中断
  • 核心需求：电源、空调等机房环境是硬件运行的基础，需通过 “冗余设计” 应对断电、环境异常。
  • 典型方案：
  • 双电源 + UPS：服务器、交换机等关键设备配置双电源，分别连接不同的 UPS（不间断电源）；UPS 连接市电 + 备用发电机，市电中断后 UPS 立即供电，发电机启动后接替 UPS，确保设备不宕机；
  • 机房冗余：核心业务部署 “异地灾备机房”（如上海主机房 + 杭州灾备机房），主机房因自然灾害（地震、火灾）无法运行时，灾备机房可接管业务。
  • 示例：金融机构的核心数据库机房配置双 UPS + 柴油发电机，市电中断后，UPS 支撑 15 分钟，期间发电机启动，确保数据库连续运行。

二、高可用核心软件组件：实现智能调度与故障处理

硬件冗余是基础，但需软件组件实现 “故障检测、自动切换、数据同步、流量调度”，才能真正达成高可用。以下是高可用体系中不可或缺的软件组件：

1. 故障检测与自动切换组件：核心 “大脑”
  • 作用：实时监测硬件 / 服务状态，发现故障后自动触发切换（如 VIP 漂移、服务接管），无需人工干预。
  • 典型工具 / 方案：
  • Keepalived：基于 VRRP（虚拟路由冗余协议）的开源工具，常用于 LVS、Nginx 等服务的主备切换。主节点正常时，通过 “心跳包” 向备节点发送状态；主节点故障后，备节点检测到心跳丢失，立即接管 VIP 和服务；
  • Corosync+Pacemaker：开源高可用集群套件，Corosync 负责节点间通信和心跳检测，Pacemaker 负责资源管理（如 IP、服务、存储挂载），支持更复杂的切换逻辑（如多节点集群、资源依赖管理）；
  • 硬件自带软件：如 F5 BIG-IP 的 “设备服务集群（Device Service Cluster）”、华为存储的 “HyperMetro”，内置故障检测和自动切换功能。
  • 示例：LVS 主备集群通过 Keepalived 实现高可用，主节点故障后，备节点在 1-3 秒内接管 VIP，客户端无感知。
2. 负载均衡组件：流量调度 + 健康检查
  • 作用：将客户端请求均匀分发到多台后端服务器，同时通过 “健康检查” 剔除故障节点，确保流量仅流向正常节点（既是性能优化工具，也是高可用核心组件）。
  • 典型工具 / 方案：
  • 软件负载均衡：Nginx（七层，支持 HTTP/HTTPS 路由）、HAProxy（四层 + 七层，支持 TCP/HTTP）、LVS（四层，基于内核，性能极高）；
  • 硬件负载均衡：F5 BIG-IP、Citrix NetScaler（性能强、稳定性高，适合核心入口）；
  • 云负载均衡：阿里云 SLB、AWS ELB（托管服务，自动扩容，无需维护硬件）。
  • 示例：Nginx 负载均衡后端 3 台 Web 服务器，通过 “TCP 端口检测”（每 5 秒检测一次 80 端口），若某台 Web 服务器 80 端口不可用，Nginx 立即停止向其转发流量。
3. 数据同步与一致性组件：确保数据不丢失
  • 作用：在多节点冗余场景（如数据库主从、缓存集群）中，确保数据在节点间同步，避免切换后数据丢失或不一致。
  • 典型工具 / 方案：
  • 数据库同步：MySQL 主从复制（基于 binlog，异步 / 半同步）、PostgreSQL 流复制（同步 / 异步）、MongoDB 副本集（1 主 2 从，自动故障转移）；
  • 缓存同步：Redis Cluster（数据分片 + 副本，主节点故障后从节点自动升级）、Redis Sentinel（主从监控 + 自动切换）；
  • 分布式一致性协议：Paxos（如 etcd、ZooKeeper）、Raft（如 etcd v3、Consul），用于分布式系统中数据的一致性存储（如服务注册发现、配置中心）。
  • 示例：MySQL 主从集群采用 “半同步复制”，主库写入数据后，需至少 1 个从库确认接收 binlog，再向客户端返回成功；主库故障后，从库切换为主库，数据丢失量极小。
4. 服务容错与降级组件：避免级联故障
  • 作用：当某部分服务故障时，通过 “熔断、降级、限流” 避免故障扩散到整个系统，确保核心服务正常运行。
  • 典型工具 / 方案：
  • 熔断器：Sentinel（阿里）、Hystrix（Netflix）、Resilience4j（轻量级），当服务调用失败率超过阈值时，自动 “熔断”（停止调用该服务），避免资源耗尽；
  • 服务降级：通过配置中心（如 Nacos、Apollo）动态关闭非核心功能（如推荐系统、积分兑换），优先保障核心功能（如购物、支付）；
  • 限流：Nginx 限流（基于 IP / 请求数）、Sentinel 限流（基于 QPS / 线程数），防止突发流量冲垮服务。
  • 示例：电商大促期间，若推荐服务压力过大，通过 Sentinel 触发熔断，自动降级为 “默认推荐列表”，避免推荐服务故障影响购物车、结算等核心流程。
5. 监控与告警组件：提前发现问题
  • 作用：实时监控硬件、软件、服务的状态（如 CPU 利用率、内存、服务响应时间、错误率），异常时及时告警，避免故障扩大（高可用的 “预警系统”）。
  • 典型工具 / 方案：
  • 基础设施监控：Zabbix、Prometheus+Grafana（监控服务器、交换机、存储的硬件指标）；
  • 应用监控：SkyWalking、Pinpoint（分布式链路追踪，监控服务调用链和响应时间）；
  • 告警工具：AlertManager（配合 Prometheus）、Zabbix Alert、企业微信 / 钉钉机器人（将告警信息推送到指定人员）。
  • 示例：通过 Prometheus 监控 Web 服务器的 CPU 利用率，设置阈值 “超过 80% 告警”，运维人员收到告警后及时扩容，避免 CPU 过载导致服务响应变慢。

三、高可用硬件与软件的协同逻辑（示例）

以 “LVS+Nginx+MySQL” 的典型 Web 架构为例，高可用硬件与软件的协同流程如下：

  1. 硬件层：LVS 主备服务器（双电源 + 双网卡）、Nginx 集群（3 台服务器）、MySQL 主从（主库 RAID5 + 从库 RAID5）、核心交换机（双机堆叠）、UPS + 发电机；
  2. 软件层
  3. Keepalived：实现 LVS 主备切换，主节点故障后备节点接管 VIP；
  4. LVS：四层负载均衡，将 HTTP 流量分发到 Nginx 集群；
  5. Nginx：七层负载均衡，将请求分发到 Web 服务器，同时健康检查剔除故障 Web 节点；
  6. MySQL 半同步复制：主库写入数据后同步到从库，主库故障后通过 MHA（MySQL 高可用管理器）自动切换到从库；
  7. Prometheus+Grafana：监控所有节点的硬件和服务状态，异常时告警；
  8. 故障场景：LVS 主节点突然宕机 → Keepalived 检测到心跳丢失 → 备节点接管 VIP → 流量正常流向 Nginx 集群 → 业务无感知。

四、总结

高可用体系的核心是 “硬件冗余消除物理单点，软件组件实现智能调度”：

  • 硬件层需覆盖 “服务器、网络、存储、电源” 四大核心，确保任何单一物理设备故障不中断服务；
  • 软件层需通过 “故障检测、负载均衡、数据同步、监控告警”，实现故障自动处理、流量合理分配、数据不丢失；
  • 硬件是基础，软件是灵魂，二者协同才能构建满足 “3 个 9”“4 个 9” 甚至 “5 个 9” 可用性的系统。

/etc/keepalived/keepalived.conf

#全局定义
global_defs {
   notification_email {
     acassen@firewall.loc
     failover@firewall.loc
     sysadmin@firewall.loc
   }
   notification_email_from Alexandre.Cassen@firewall.loc
   smtp_server 192.168.200.1
   smtp_connect_timeout 30
   router_id LVS_DEVEL
   vrrp_skip_check_adv_addr
   vrrp_strict
   v
}
# 定义Vrrp的实例
vrrp_instance VI_1 {
    state MASTER   #状态master/backup
    interface eth0   #绑定网络接口
    virtual_router_id 51   #虚拟路由的ID；作用：判断 51 backup 51    取值范围（1-255）
    priority 100   #优先级   取值范围（1-255） 值越高优先级越高
    advert_int 1     VRRP 以秒为单位的通告（宣告）间隔 
    authentication {   #验证机制
        auth_type PASS
        auth_pass 1111
    }
  #定义虚拟IP地址(vip)
    virtual_ipaddress {
        192.168.200.16
        192.168.200.17
        192.168.200.18
    }
}
# 虚拟主机地址
virtual_server 192.168.200.100 443 {
    delay_loop 6   #延迟循环次数
    lb_algo rr         #loadblance  算法： rr 
    lb_kind NAT  #loadblance   调度模式
    persistence_timeout 50   #  LVS持续超时间（以秒为单位），默认为6分钟
    protocol TCP   #协议类型： TCP
#定义后端真实主机地址
    real_server 192.168.201.100 443 {
        weight 1
        #检查后端真实主机的健康检查的协议类型
        SSL_GET { }
        TCP_CHECK { }
        HTTP_GET {
            url {
                path  /index.html
            }
        }
}
